# 核心方法论 · 必备六件套详解

> 任何赛题完成的判定标准 = 六件套齐全 + 可编译 + 有量化指标 + 有踩坑沉淀。
> 这个文件告诉你**每件套到底写什么、不写什么、写到什么程度算合格**。

---

## 件 1：`00_深度审题与方案论证.md`（审题件）

### 必须包含

1. **题目核心拆解**（用自己的话复述，不能贴原文）
   - 输入：什么信号 / 什么数据 / 什么场景
   - 输出：什么物理量 / 什么决策 / 什么得分点
   - 约束：电压电流上限、时间限制、空间限制、禁用器件
2. **指标量化清单**（关键！）
   - 把题目里所有定性词（"准确"、"快速"、"稳定"）翻译成数字
   - 例：误差 ≤ 1%、响应时间 ≤ 100ms、跑完一圈 ≤ 30s
3. **多方案对比表**（≥2 套）
   ```markdown
   | 方案 | 核心思路 | 性价比 | 难度 | 风险 | 评分 |
   |---|---|---|---|---|---|
   | A | xxx | ★★★★ | ★★ | 元器件难买 | 32 |
   | B | xxx | ★★★ | ★★★★ | 时间不够 | 28 |
   ```
4. **评审打分**（总分 100）
   - 性能（30）
   - 实现难度（20）
   - 物料可得性（20）
   - 团队熟悉度（15）
   - 风险可控性（15）
5. **最终选型 + 理由**（一段话，敢拍板）
6. **风险登记册**（≥3 条潜在炸点 + 应对预案）

### 不要写

- ❌ 复制粘贴官方原题（那是 `00_题目原件.md` 的事）
- ❌ "我觉得 / 大概 / 应该"——所有判断都要有依据
- ❌ 拖到代码写完才补审题（这违反顺序原则）

## 件 2：`01_代码/`（代码件）

### 强制分层

```
01_代码/
├── Core/         # 主循环、状态机、业务编排
├── Drivers/      # 与硬件/SDK/IO 直接打交道的封装
├── Algorithm/    # 纯逻辑、可单测、可平移到 PC 跑
├── config.h /    # 集中管理可调参数
│   config.toml /
│   config.py
└── README.md     # 编译运行说明
```

**铁律**：

- 驱动层不写业务，业务层不直接读寄存器
- 算法层禁止 `#include "stm32xxx.h"`，要让它能在 PC 上跑测试
- 所有"可能要调"的数字（PID 系数、阈值、采样率、超参数）放 `config.*`
- 每个文件 < 500 行，超了拆

### `README.md` 必须回答

1. 怎么编译（一行命令）
2. 怎么烧录 / 怎么运行
3. 用了哪些硬件 / 哪些库（含版本）
4. 引脚分配 / 端口分配表
5. 预期输出长什么样

### 软件比赛/ICPC 的变体

- `Core/` → `solution/`（每题一个 cpp）
- `Drivers/` → `io/`（输入解析、输出格式化）
- `Algorithm/` → `algo/`（DSU、SegTree、几何模板等）
- `config.h` → `template.cpp`（含常用头文件 + 宏）

## 件 3：`02_硬件/` 或 `02_环境/`（环境件）

### 硬件比赛（电赛/智能车/RM）

- `电路设计说明.md`：每个模块为啥这么设计、关键元器件选型理由
- `材料清单_BOM.md`：序号 / 名称 / 型号 / 参数 / 数量 / 用途 / 备注 / 单价 / 链接
- 原理图 PDF / PCB 截图 / 实物照片

### 软件比赛

把这个目录改名为 `02_环境/`：

- `依赖清单.md`：Python/Node/CUDA 版本、关键 pip 包及版本
- `Dockerfile` 或 `requirements.txt` / `pyproject.toml`
- `数据集说明.md`：数据来自哪、怎么下载、目录结构

### 算法比赛

可裁剪为 `02_环境/`：

- 编译选项（`-O2 -std=c++17`）
- 评测机配置（如果赛会公布）
- 本地测试脚本

## 件 4：`03_报告/`（报告件）

### 八段式模板（电赛/智能车/RM 通用）

1. **摘要**（200~300 字，含核心指标）
2. **方案比较与选择**（来自审题件）
3. **理论分析与计算**（公式推导，写出关键参数怎么算的）
4. **电路与程序设计**（结构图 + 关键代码片段）
5. **测试方案与数据**（测试条件 + 数据表 + 误差分析）
6. **创新点**（≥2 条，要有"对比基线"才算创新）
7. **结论**
8. **参考文献**

### 算法比赛变体

报告 → `题解.md`：题意复述、思路、复杂度、关键代码、踩坑。

### 数模变体

报告 → `论文.tex`：摘要 / 问题重述 / 假设 / 模型 / 求解 / 验证 / 灵敏度 / 优化 / 结论。

### 评分要点（不管什么比赛都通用）

- 摘要必须包含数字
- 测试数据必须有"测试条件"和"重复次数"
- 创新点要可对比（"我用 X 取代了传统 Y，提升了 Z%"）
- 不要出现"很好"、"非常好"——评委只看数字

## 件 5：`04_调试记录/`（沉淀件）

### `调试检查清单.md`

按"上电前 / 上电后 / 跑代码 / 验收"四阶段列 ToDo：

```markdown
## 上电前（10 分钟）
- [ ] 万用表测电源极性
- [ ] 烧录器接线方向
- [ ] 母线电容焊向
- [ ] ...

## 上电后（5 分钟）
- [ ] LED 是否点亮
- [ ] 调试串口能否输出
- [ ] ...
```

### `独到经验总结.md`

每条经验三段式：

```markdown
### 经验 N：<一句话标题>

**踩坑现象**：<具体看到了什么不正常>
**根因分析**：<为什么会这样，有理论依据，不是猜>
**解决方法**：<具体改了哪行代码 / 哪个参数 / 接了哪根线>
**复用价值**：<下次遇到类似题怎么直接拿来用>
```

**铁律**：经验总结至少 3 条，不能写"调通了，没啥可说的"。
没有经验=没认真做。

## 验收脚本（可写成 CI）

伪代码：

```python
required = [
    "00_深度审题与方案论证.md",
    "01_代码/README.md",
    "02_硬件/材料清单_BOM.md",  # 软件比赛换成 "02_环境/依赖清单.md"
    "03_报告/设计报告.md",
    "04_调试记录/调试检查清单.md",
    "04_调试记录/独到经验总结.md",
    "00_题目原件.md",
]
for f in required:
    assert exists(f) and size(f) > 200, f"{f} 缺失或太短"

assert lint("01_代码/").errors == 0
assert count_quantitative_metrics("00_深度审题与方案论证.md") >= 5
assert count_lessons("04_调试记录/独到经验总结.md") >= 3
```

把这个跑通，这道题就算"完成"了。
