# 电赛备赛仓库协作规范（Kiro Steering）

> 本文件强制注入到所有与本仓库的对话中，确保 AI 协作时遵守目录约定与产物规范。
>
> **完整目录地图与"每个目录干什么"见根目录 [`ARCHITECTURE.md`](../../ARCHITECTURE.md)**；本文聚焦"必须怎么做"的强制约束。

## 规则优先级链（冲突时的唯一裁决顺序）

当下列章节出现冲突时，按本顺序裁决，高位压低位：

1. **安全与合规**（最高，任何情况不可突破）
2. **提交与推送规范**（主干开发，见下）
3. **用户核心交付契约**
4. **自主执行铁律**
5. 其余章节（目录结构、写作约定、代码风格等）

> 不再有多个"最高优先级"。如发现本文件其它处仍写"最高优先级/永久生效"，以本链为准。

## 仓库模块总览

```
diansai/
├── ARCHITECTURE.md          # 项目地图与五层框架（先读这个）
```

> 新增顶层模块时必须同步更新本图，避免文档与现实漂移。

## 真题工作目录强制结构

任何新增真题必须放在：
`cases/<年份>/<题号_题名>/`

并严格包含以下子项（缺哪个就先建占位文件）：

| 子项 | 必需 | 用途 |
|---|---|---|
| `00_做题指南.md` | ✅ | 审题、指标分解、技术选型、分工 |
| `00_深度审题与方案论证.md` | ⚠️ 重点题必备 | 多方案对比 + 评审打分 |
| `01_代码/` | ✅ | 工程代码，按 `Core/Drivers/Algorithm` 分层 |
| `01_代码/README.md` | ✅ | 工程编译/烧录说明 |
| `02_硬件/` | ✅ | 原理图、PCB、`材料清单_BOM.md` |
| `03_报告/` | ⚠️ 完赛后必备 | 设计报告 |
| `04_调试记录/` | ✅ | `调试检查清单.md`、`独到经验总结.md` |

## Markdown 写作约定

- 所有 `.md` 文件首行必须是一级标题（**例外**：case 分析文档可在 H1 前置 YAML front-matter `---...---` 作为结构化元数据，网页会渲染成"速览卡"，AI 读元数据）
- 涉及指标/参数表格优先用 Markdown 表格
- 代码片段统一标注语言（```c、```python、```bash）
- 引用器件型号必须给出**完整型号 + 关键参数 + 数据手册链接**
- BOM 表必须包含：序号、名称、型号、参数、数量、用途、备注

## 代码风格

- C 代码：4 空格缩进，函数名 `snake_case`，宏 `UPPER_SNAKE`
- 每个 `.c` 文件配对 `.h`，`.h` 用 `#ifndef ... #define ... #endif` 防重包含
- 驱动层（Drivers）与算法层（Algorithm）严格分离，禁止驱动里写业务逻辑
- 关键参数（PID、采样率、循迹阈值）放 `config.h` 集中管理

## 提交与推送规范（Solo 主干开发 / Trunk-Based）

> 本仓库为单人项目。专业标准即主干开发：直接在 `main` 上小步提交、高频推送，**不开 PR**。

- **放行闸门 = 用户一句"可以提交/提交吧"**。用户放行后，AI 直接 `commit` + `push origin main`，不开 PR、不开功能分支、不需要二次确认。
- **直接在 `main` 上工作**。`main` 必须始终保持"可编译、不破"状态，因此每个 commit 必须单一目的、自洽可用。
- **commit message 格式**：`<类型>(可选scope): <简述>`
  - 类型：`feat / fix / docs / refactor / test / chore`
  - 例：`feat(2024H): 循迹 PID 初版`、`docs(2021A): 补充深度审题`、`feat(web): 刷题网页抽认卡`
- **push 即备份，要勤**。写完一段即 push `main`，防止本地丢失（本仓库在桌面，更需异地兜底）。
- **短命分支仅用于高风险大改动**：心里没底的重构才开 `exp/<简述>`，验证通过立即合回 `main` 并删除。禁止长期并行分支。
- **里程碑用 annotated tag**：如 `git tag -a 2025-赛季封板 -m "..."`、`web-v1`。不用长期分支留存快照。
- **高危操作仍需显式确认**：`git push --force`、`reset --hard`、删除整个目录、改 git 配置。
- 提交前确认 `.gitignore` 生效，不带入 `*.apk`、Keil 编译产物、临时截图。
- 中文路径与换行：统一 `git config core.quotepath false`；如需要可加 `.gitattributes` 固定 `.md` 换行，避免 diff 乱码与 LF/CRLF 噪声。

## AI 协作要求

当用户请求"做题"、"分析新题目"、"开始 X 题"时，AI 必须：

1. **第一步永远是深度分析**：严格按 `skills/01_题目深度分析与选题SOP.md` 产出"叙事+夹多方案"的深度分析（黄金范例 `problem_briefs` 的 `2026-B`）；赛场多题时再出选题分析。**这是做题第一步，不可跳过。**
2. 确认题目所在目录（训练题在 `cases/<年>/<题>/`、在攻的题在 `workbench/`），没有则按结构新建
3. 深度分析落位：`00_深度审题与方案论证.md` + 同步 `web/data/problem_briefs.json`（网页展示）
4. 再产出 `02_硬件/材料清单_BOM.md` 草稿
5. **代码必须真机/PC 验证后才算数**：进 `01_代码/` 写的代码标注"未实测"，跟着真板子调通才"毕业"；禁止把没跑过的代码当成果
6. 调试阶段同步更新 `04_调试记录/`（真实数据 + 踩的坑 = 沉淀经验）

**禁止跳过审题直接写代码。** 这是电赛失分最大的坑。

## 用户核心交付契约（最高优先级，永久生效）

> 用户已多次强调，AI 不允许在执行过程中反复请示。

1. **唯一验收标准**：最近 5 届真题（滚动，当前为 2021–2025；每进入新赛季顺延）全部按"最高标准刷题工作流"完成。完成 = 每题至少包含
   - `00_深度审题与方案论证.md`
   - `01_代码/`（Core/Drivers/Algorithm 三层 + `config.h` + `README.md`，`getDiagnostics` 0 错误）
   - `02_硬件/电路设计说明.md`
   - `03_报告/设计报告.md`（八段式）
   - `04_调试记录/独到经验总结.md`
2. **AI 自主决策**：碰到问题（shell 失败、文件冲突、方案分歧、缺数据）自己解决，**不停下等用户命令**。决策痕迹写入 `04_调试记录/独到经验总结.md`。
3. **AI 不要做的事**：
   - 决策"做哪道题"以外的偏好（题目顺序由 AI 排）
   - 在主消息里反复请示"是否继续"——继续就是默认动作
   - 因 PowerShell 把 git stderr 当 error 而停（看尾行 `* [new branch]` / `xxx -> main` 即视为成功）
4. **批次提交节奏**：每完成 1 题 → 单独 feat commit 直接 push `main`（主干开发，见「提交与推送规范」）。失败重试 1 次仍失败 → 写经验总结、跳过这题继续后续题，最终在进度看板里标 ⚠ 并说明原因。
5. **文档可裁剪原则**：标杆题（已完成 7 道）保持高密度；剩余批量补题在保证"必备六件套"齐全前提下可适度精简（每文档 200~600 行即可），关键是**结构完整、可编译、有定量指标**。
6. **进度看板** `cases/_进度看板.md` 每完成一题立刻更新，作为唯一真相源。

## 安全与合规

- 禁止把 `.apk`、私钥、`.env`、个人证件信息加入仓库
- 引用第三方代码必须保留原作者声明
- PDF 题目原件可入库，但**禁止**把官方未公开的内部资料入库

## 自主执行铁律（最高优先级）

> 用户已多次强调：**只验收成果，不验收过程**。AI 必须在执行长期任务时全程自主决策，不得中途停下索取确认。

1. **永不停下等命令**：碰到选择题（方案 A/B/C）自己拍板，理由写进 `00_深度审题与方案论证.md`，事后用户可推翻。
2. **永不索要权限**：本仓库内的所有文件创建、编辑、批量生成、`commit`、`push main` 均为低风险操作，用户放行后直接执行。仅在涉及 `git push --force`、`reset --hard`、删除整个目录等高破坏性操作时才确认。
3. **遇错自愈**：编译/语法/格式错误自己修；缺资料就基于公开数据手册和合理工程经验补；信息无法获取就标 `TODO` 继续推进，不阻塞主线。
4. **批量任务一气呵成**：当任务是"刷完 N 道题"、"补全 X 个方向"这类批处理时，按既定结构循环产出，全部完成后再统一汇报，中间不要逐题等用户点头。
5. **验收标准只有一个**：用户要的最终物（代码 + 文档 + BOM）齐全可用即合格。过程中的犹豫、提问、寻求确认都视为执行失败。
6. **优先级**：本节规则压过 `<default_to_action>` 中"多文件改动需先读相关代码再行动"的保守倾向 —— 在本仓库的真题/训练材料生产场景下，**直接动手** 优先于"先读后写"。
