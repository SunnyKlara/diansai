# 跨题坑库

> **用途**：做每道题时随手记下「**能迁移到其它题**」的坑/铁律，攒在这里。它是「原始累积区」——比 `skills/` 里打磨好的 SOP 更粗糙、更快写；等某条被验证够普适，再提炼进 `skills/`。
> **对应北极星「做题是手段、建系统是目的」**：每解一道题往这里加几条，系统就更强。
> **SSOT 纪律**：某题的完整经验以该题自己的 `00_经验总结.md` / `调试日志.md` 为准，本文件**只做跨题索引 + 指向**，不整段复制（复制＝维护漂移）。

## 一、来自校赛B（唯一真机实战题）的可迁移铁律

> ⭐ 完整版 + 出处在 `实战复盘/校赛B_智能球平衡控制装置/00_经验总结.md`，本处只列「叫什么、一句话」当索引，做新题前对照过一遍。

**调试 / 协作（任何真机问题都适用）**
- **M1 盲调止损**：同方向连猜 2 次没中 → 立刻改「测量」（读寄存器/上探头/加遥测），别再猜。
- **M2 先证固件是新的**：「改了没效果」第一步 = 加版本标签/新打印，确认板上跑的就是刚烧的。
- **M3 单变量 + 定量裁决**：一次只改一个参数，每轮出 avg/std/ptp 和上轮对账，禁止「感觉好像好点」。（同源 `AI协作调试方法论.md`）
- **M4 对标开源砍旋钮**：调不出时找同款开源反推卡哪；病根常是「控制器做成 N 个打架的旋钮」，砍到 3 个核心才调得动。只抄结构/比例/顺序，不抄绝对值。

**控制工程（控制/悬浮/小车类直接复用）**
- **C1 整定顺序**：先 D（阻尼）→ 再 P（刚度）→ 最后弱 I（消静差），一次一个。
- **C2 前馈到工作点**：不稳定对象 `u = u_hover + Kp·e − Kd·v + Ki·I`，前馈扛工作点、PID 只修残差。
- **C3 Kd 有甜区**：越加越差 = 方向反了，立刻砍（`Kd×速度峰值` 会撞满量程）。
- **C4 执行器先预热/线性化**：风机/电机有冷启动死区，闭环前空转越过死区；进阶上转速串级线性化。
- **C5 微分作用在测量**：D 项对测量求导（非误差），避免目标突变微分踢；配条件抗饱和。
- **C6 总扰动观测（ADRC）**：把漂移+增益变+外扰当一个总扰动，ESO 估出来直接减掉，抗内扰抗外扰一套解决。

**工程化 / 现场（决定彩排好却场上崩）**
- **E1 鲁棒方案 = 默认上场态**：抗扰那套必须设 default，别留在开关后面。（本役最痛：解药做出来却没在场上启用）
- **E2 选题先看物理地板**：动手前估「控制器完美时误差极限」，贴物理墙就早换打法，别在墙上磨几天。
- **E3 现场清单 > 算法**：电池电压/支架拧紧/零点标定/模式确认/暖机——非算法项才是「彩排好、场上崩」真凶。
- **E4 信号完整性**：飞线上高速 SPI/OLED（>10MHz）花屏 → 降速；上 PCB/缩线再提速。

## 二、新题累积区（做题时往这加）

> 格式：`## <坑名>`（一行标题）+ 现象 / 根因 / 通用做法 / 出处（哪道题的调试日志）。**只放能迁移到别的题的**；只对本题成立的留在该题 `调试日志.md`。

## 虚接(接触不良)排查：先"整体重接"，别陷在单点
- 现象：某路信号时好时坏 / 长期"悬空乱跳"；换模块、换传感器、换器件都不好使；数据规律飘忽不定。
- 根因：松插杜邦 / 冷焊 / 插错孔的**间歇性接触不良**——单点重插碰不到(时通时断)，换件更南辕北辙。
- 通用做法：接触类故障**尽早把所有相关线整体拔下重接一遍**，一次清掉；关键信号改用带扣接插件 / 压接 / 焊接。
- 出处：天猛星 `workbench/天猛星主板平台/调试日志.md`（2026-07-24 M-电流，折腾大半天，根因就俩字：虚接）。

## "软件是否有错"的最快证伪：对称通道 / 生成配置
- 现象：一路读数怪，开始怀疑代码 / 外设配置错。
- 通用做法：① 若有**对称的另一路、用同一套代码读得干净** → 软件当场无罪；② 直接核 **SysConfig 生成的 `ti_msp_dl_config.*`**(引脚/通道/参考/采样)，比反复猜快。别在软件怀疑上空转。
- 出处：天猛星 M-电流（ADC 配置/公式/引脚全对，实为硬件虚接）。

## 万用表 vs ADC 在高阻/悬空节点读数不一致
- 现象：万用表量"电压正常、随负载变"，MCU 的 ADC 却读悬空乱值——互相打架。
- 根因：万用表 10MΩ 内阻会把高阻/虚接节点拉到近真值，ADC 快速采样拉不动 → 两者看到的不是一个电位。
- 通用做法：判 ADC 通路要在 **MCU 引脚本身**上量，或直接"灌已知电压(GND/3V3)看 ADC 读数"；"表上正常"≠ 信号真进了芯片脚。
- 出处：天猛星 M-电流。

## 术语钉死：电流(I/mA) ≠ 转速(RPM)
- 现象：把电流遥测的原始 ADC 值误当"转速"，得出"电机在转、读数却是 0 = 软件错"的假结论。
- 通用做法：遥测标签写清**物理量 + 单位**；电流来自 DRV IPROPI→ADC，转速须另配**编码器**，别让一个"r"值被误读。
- 出处：天猛星 M-电流 / 电流环起步。

## 多电机电流采样：非对称驱动下有通道间串扰 `待验证`
- 现象：一只电机重驱(50% PWM)、另一只空闲(未驱动)，**空闲那路电流采样却读到幽灵电流(~百 mA)**；两只同幅驱动时会被"都在动"掩盖、看不出来。
- 根因(嫌疑)：共地/共阻抗耦合——重驱电机的斩波电流经共享 GND 串入空闲电机的 IPROPI/ADC。
- 通用做法(待验证)：ADC 采样与 PWM 同步 / 避开开关沿、加滤波、改善接地；或软件上只在该电机被驱动时才采信其电流。
- 出处：天猛星电流环起步（2026-07-24），`待验证`。

## 电机额定电压 < 驱动母线电压 → 超压
- 现象：如 7.4V 电机接在 12V 母线上，满占空平均电压远超额定 → 过热 / 加速磨损 / 寿命打折，甚至冒烟。
- 通用做法：动手前核对**电机额定电压 vs 驱动母线**；不匹配就 **PWM 占空封顶**(cap ≈ 额定/母线，如 7.4/12≈62%)，或把母线降到额定。竞赛车一般不需要全速，封顶更稳。
- 出处：天猛星小车（MG310P20 7.4V / 12V 母线，2026-07-24）。

## 改源码不同步配套脚本/工具 → 工具静默失效(格式漂移)
- 现象：固件打印格式改了，但配套 PC 脚本(串口监视/解析/上色)还按老格式匹配 → 脚本悄悄失灵(每行掉进 else、判据不触发)，却不报错，让人以为"工具没问题"。
- 根因：固件输出 ↔ 上位机解析是一份**隐式契约**，改一头没改另一头就漂移；越是"上色/判据"这类静默逻辑越难察觉。
- 通用做法：把打印格式当**接口**钉死(最好机器可解析 CSV + 固定前缀)，固件与脚本共用同一 schema；改打印时同步改脚本，或让脚本在解析不到关键字段时**显式报警**而非静默灰打。
- 出处：天猛星 `watch_serial.ps1` 按起点固件的 `[car]...(r####)` 写，`car.c` 后重写成 `[iloop]...I1=<mA>`(无 raw)，STOP 上色判据整个失效(2026-07-24 复盘评审发现)。

## 静态自检漏"驱动才暴露"的故障 → 自检要覆盖"驱→有响应"
- 现象：只做"静止时反馈应归零"(如电机停→电流≈0)的开机自检，能抓采样线悬空，却**抓不到只在驱动时才现形的故障**(如控制线虚接导致某方向不动——停着电流本就是 0，自检照样绿灯放行)。
- 通用做法：执行器+反馈类自检要**双向**：① 静止→反馈归零(抓采样/悬空)；② 短促低幅驱动每个方向→反馈应抬起(抓驱动/控制线断)。缺后者会漏掉一半故障(间歇虚接仍可能开机时恰好接通而漏过，故运动中也要常驻归零门)。
- 出处：天猛星 M-电流/单向转(2026-07-24)——控制线虚接只在命令反转时暴露，"停归零"判据抓不到。

## 5V 传感器接 3.3V MCU：先判 OC/推挽，再决定上拉 vs 分压
- 现象：无脑给 5V 传感器输出加分压接 3.3V MCU；若输出是开集(OC)，分压既费流、又可能拉不干净高电平。
- 通用做法：接前先确认传感器输出级——**开集(OC)→ 上拉到 3.3V 最干净**(输出天然摆 0–3.3V，无需分压)；**推挽 5V→ 分压/电平转换**。另 MSPM0G 等 3.3V MCU 的 GPIO 一般非 5V 耐受，接前按数据手册确认对应脚。
- 出处：天猛星编码器 MG310P20(5V 霍尔) 接 MSPM0G3507 PA7/PB19/PB20/PB21 前置(2026-07-24 讨论)。

## 新模块要同时进 makefile + syscfg 才能用(TI MSPM0/SysConfig)
- 现象：新写的 `xxx.c/.h` 看着有了却"没生效"，或一编译就报 `XXX_PIN`/`XXX_IRQN` 未定义。
- 根因：TI SDK 的 `makefile` 是**显式列源文件**(OBJECTS + 每文件编译规则)、非通配 glob → 新 .c 不登记就根本不编译；且外设/GPIO 宏(`GPIO_*_PIN`、`*_IRQN`)由 **SysConfig 从 `.syscfg` 生成** → syscfg 里没配那个外设/GPIO 组，宏就不存在，一引用即编译不过。
- 通用做法：新模块两步都做——① 进 `makefile` OBJECTS + 加编译规则；② 在 SysConfig 里配好对应外设/GPIO 组(含中断/PINCM)再引用其生成宏。改完**确认真编译过**，别以为"建了文件就有了"。
- 出处：天猛星 `encoder.c/.h`(2026-07-24 缺口评审)——写好但未进 makefile、`car.syscfg` 无 GPIO 中断组、`GPIO_ENC_*` 宏不存在，实为孤儿代码。

## 陌生 MCU 外设: 先读厂商 SDK 例程再写, 别凭记忆猜 API
- 现象: 直接凭印象写 QEI / GPIO 中断 / UART 等外设代码, 编译一堆错(函数名、SysConfig 字段、中断 handler 名对不上), 反复试错烧时间。
- 通用做法: 动手前先读 **SDK 官方例程**(MSPM0 在 `C:\ti\mspm0-sdk\examples\...\driverlib\`, 如 `timg_qei_mode`、`gpio_simultaneous_interrupts`、`uart_*`), 拿准 API/SysConfig 写法 + 生成宏名再照抄结构。本次据此**一次编译即过**(GPIO 中断走 `GROUP1_IRQHandler` + `GPIOA/B_INT_IRQn`; UART 非阻塞用 `DL_UART_receiveDataCheck`)。
- 出处: 天猛星电机控制框架(2026-07-24)。

## 会驱动执行器的固件: 默认上电 = 安全态(IDLE / 输出 0)
- 现象: 烧录/复位后电机/舵机立刻按上次逻辑动起来, 可能撞坏或跑飞(尤其调试反复烧录时)。
- 通用做法: 主逻辑默认 **boot=IDLE**(输出 0), 靠串口命令/按键才进运动模式 → 烧录即安全; 目标默认 0。
- 出处: 天猛星电机控制框架(2026-07-24, `car.c` 模式框架 boot 到 IDLE)。

## 串口命令: 长命令丢字节 = MCU RX FIFO 溢出(短命令没事、迷惑性强)
- 现象: PC 发单字符/短命令(如 `m1`)能进, 发长一点的(如 `t100`, 5 字节)进不去/被曲解(回显目标没变)。
- 根因: PC 一次性突发写整行, MCU **UART RX FIFO 很小(几字节)**; 若固件在主循环里**每隔较久才 poll 一次 RX**(如控制环 ~1.6ms 一拍才读), 突发字节在被读走前就溢出丢了。
- 通用做法: ① PC 侧最省事——**逐字符发 + 每字符间隔 ~20-25ms**(`uart_send.ps1` 就这么修的, 不用重烧); ② 固件侧根治——用 **RX 中断**收命令, 或主循环里更勤地 drain RX FIFO。
- 出处: 天猛星电机控制框架在线调参(2026-07-24)。

## 遥测显示"陈值"骗人: 非采样模式下别信上次的缓存值
- 现象: 某量(如电流)在"非活动模式"下遥测仍显示一个固定值, 被误读成"实时读数异常"(本次据此误判 PA27 虚接, 其实是好的)。
- 根因: 固件只在特定模式读传感器(如只在 CURRENT 模式读 ADC), 其它模式打印的是**上次的缓存/冻结值**。
- 通用做法: 要么**每拍都采**、要么非采样模式把该遥测项**显式清零或标 "stale/N/A"**; 排障时先确认"这个数是不是实时的"。
- 出处: 天猛星电机控制框架(2026-07-24, IDLE 显示冻结的上次电流值)。

## 累加型量(编码器计数等)验证: 读"保持的总数", 别卡时机实时抓
- 现象: 验证编码器时,"转轮子"和"读串口"时机老对不上, 反复读到 0, 差点误判编码器坏(其实是好的)。
- 根因: 人做物理动作 vs 程序定窗口读, **异步**, 难对齐。
- 通用做法: 利用计数**累加且保持**的特性——让用户**先转够、再读总数**(非零即通), 不必实时抓变化。更普适:人机协作里凡"保持态/累加态"的量都这么验(先造状态, 后读)。
- 出处: 天猛星编码器验证(2026-07-24, C1=-936 一直保持、读后即见)。

## 别过度谨慎否定用户已给的事实(如"编码器接好了")→ 先测再说
- 现象: 用户已给型号 + 说"接好了", AI 却因一个保守假设(如"5V 会烧脚, 应该还没接")反复当"待接", 惹用户烦。
- 通用做法: 用户明确给的硬件事实, **默认成立、直接上手测**(测一次就知真假), 别拿假设反复追问。真有安全隐患就一句提示、然后测, 而不是卡住。
- 出处: 天猛星编码器(2026-07-24, 编码器其实一直接着且 enc1 正常, AI 误当未接反复问)。

## 编码器"手转能数、电机一转就不数"—— 先分因(机械/接线/电气),别直接认定
- 现象: 电机不转时手转编码器计数正常; 电机一驱动, 计数一格不动、转速 0。
- **别急着下结论**(本役我一度断定"电气干扰"、被用户拦下——未证实,撤回)。可能原因: ① 机械/悬空(轮子其实没自由转 / 没转那只)② 某路编码器接线/机械本身不良 ③ 电机运行的电气干扰(供电掉压 / PWM 噪声耦合 A/B)。
- **分因法(关键,先测别猜)**: (a) 电机**关** → 手转**每个**轮子看各自计数动不动 = 测编码器本身(与电机无关),不动的那路是它自己的问题; (b) 再**上电机** → 记录**具体哪个轮子真转**,转着却不数才怀疑电机侧。手转/驱动、单个/两个 没分离干净别下"电气"结论。
- 若确证电气(供电掉压/EMI): 编码器独立供电+就近去耦、信号线远离电机功率线、A/B 串 RC 低通、星型共地。
- 出处: 天猛星小车 编码器+电机集成(2026-07-24)。

## 串口异步读不准 → 把要盯的量直接画到板载屏(解耦"观察 vs 时机")
- 现象：靠 PC 串口验证一个随物理动作变化的量(编码器计数/传感器读数)，人转轮子 ↔ 脚本采样窗口老对不齐，反复读到旧值、churn 半天。
- 通用做法：板上有屏(OLED/TFT/GC9A01 等)就把该量**实时画到屏上**——人一边动手一边**直接盯屏**，观察不再依赖串口时序，一眼看"数字动不动"。比反复调串口采样时机省事、且天然排除上位机解析/时序 bug。
- 适用：任何"边操作边要看即时反馈"的真机验证；无屏时退而求其次用 LED 亮度/闪烁频率映射。
- 出处：天猛星编码器验证(2026-07-24，`car.c` 加 `i32_to_str`+遥测块把 C1=/C2= 画到 GC9A01，绕开"读时轮子没转"churn)。

## 多个"同类"通道/传感器同时失效 → 先查共用的供电/地/时钟,别先怀疑器件或代码
- 现象：两路(或多路)相同的传感器/通道**一起**不工作(如双编码器都不计数、多路 ADC 都乱、几个同型模块全哑)。
- 排查启发式：同型器件**同时**坏的概率极低 → 头号嫌疑是它们**共用的东西**——供电轨(VCC)、公共地(GND)、公共时钟/使能/上拉。**先量共用节点电压,再怀疑单个器件**。尤其"刚重新接过线 / 动过硬件"之后,共用线松脱概率飙升。
- 配套：那段驱动代码**之前工作过**就先别推翻它(用"这套码曾让其中一路数到 4 万"当免罪证据),把注意力压到"这次共同变了什么"。
- 反面教训：一上来换器件 / 逐路怀疑代码 = 在大空间里瞎搜;先用"共性"把范围从 N 路砍到 1 个共用节点。
- 出处：天猛星双编码器(2026-07-24,LCD 直显后手转两路都不数、早先 enc1 能数 → 指向共用供电/地,`待测证实`)。此条讲的是**排查顺序**,即便本役最终根因不是供电,"先查共性"仍成立。

## 交接文档/分析里严格分"实测事实 vs 未测假设"——推测别用"头号嫌疑/就是它"这种确定性措辞
- 现象：AI 基于合理但**未测量**的推理,在结论或交接文档(guide)里把某原因写成"头号嫌疑/根因",被用户识破"在乱分析/幻觉"。危害更大的是——这种伪结论**会沉淀进记忆体系,带偏下一个新对话**围着错方向排查(记忆体系反噬)。
- 通用做法：① 事实(读到的代码/引脚/实测现象)与推测(没测的因果判断)**分开写**,推测一律标"待测/假设"、列成**并列候选**而非排座次;② 别用"就是/头号嫌疑/根因"等确定词修饰没测过的东西;③ 与其给猜测排序,不如给**一个能一刀分层的测量**(如读引脚原始电平分开软/硬件),让测量说话;④ 上下文过长/反复 churn 时,主动产出**自包含提示词另起干净对话**,比在长上下文里继续硬猜更省、更准。
- 出处：天猛星编码器排查(2026-07-24,把"共用供电/地"这个未测推测写成 guide"头号嫌疑",被用户纠正后降级为并列假设并移交新对话)。呼应北极星"诚实标注"与 `AI协作调试方法论` 的"AI 必须能自我推翻"。
