## 2026-07-24 · 天猛星编码器"不计数"全程排查并修复（commit 90c1c8c `fix(mspm0)` + 配套 docs commit）

- **做了什么**：从"手转也不计数"一路排到**两路干净计数(真机验证)**。根因链：① 编码器 5V 信号**直连** 3.3V MCU 脚过压 → 中断风暴(计数虚高) → ② 加"1k串+2k对地"分压 → 因是**开集(OC)输出**被对地钳死 → **完全不计数** → ③ 拆 2k 对地 + 编码器供电 5V→3.3V + 四脚上拉 → 救活但**电机 EMI 致边沿抖、中断计数虚高~50x** → ④ **改 `encoder.c`：边沿中断解码 → 定时采样 4x 正交解码(`encoder_poll` 每 tick)→ 治本**，真机 enc1/enc2 均 `I≈4×E` 干净、方向对、静止冻结。顺带：电流采样通道按实测校正(M1↔PA26/MEM1)、`ENC_CPR` 225→899(4x)、`ENC_PROBE`→0 回控制固件。
- **关键决策/被推翻**：`已作废`「软件开迟滞+上拉即可修」= 5V直连事实曝光前的错判；`已作废`「分压降压」= 没先判 OC/推挽就荐分压，对开集输出是错的(应上拉)。最终治本 = **采样解码**(外部上拉治"慢沿"有用、治"电机EMI快毛刺"无用)。
- **协作方式**：AI 自主编译/烧录/读串口(openocd + COM30) + **分层探针**(原始电平L / 软件轮询E / 中断I 三视图) + **电机自动轻转替手转**(电流佐证真转)；用户接线/供电/示波器/万用表。
- **可迁移经验**(已入 `跨题坑库.md`)：分层探针分软硬件、多路读数锁步=共模电源地、开集要上拉别分压对地、内部上拉仍读0=外部强对地、中断计数≫轮询=风暴、采样解码>上拉治EMI、屏灭先SWD+串口验非砖、遥测变慢=中断吃CPU探针、静止读上拉电平不证线接好。
- **真值源**：`workbench/mspm0/car/{encoder.c,car.c,motor.c,car.syscfg}`。**剩(不阻塞)**：手转 N 整圈实测微调 `ENC_CPR`；电机 EMI 串扰调试UART(不影响计数)。

## （十九）ESP32-P4 屏板：ESP-IDF v5.5.4 安装路线的四个决策（2026-07-27）

> 结论已进 `CONTINUATION_GUIDE` 与 `workbench/ESP32P4_屏板/README.md`，踩坑判据成体系进了 `跨题坑库.md`。这里只留**为什么这么选**，免得下次重新纠结。

1. **不用官方 installer、不用 `git clone --recursive`，用 release zip + 国内 CDN**
   - clone 实测：主仓 depth1 ~250 KiB/s，submodule 阶段掉到 **40 KiB/s**，30+ 子模块要 1 小时以上 → 放弃。
   - 选 `dl.espressif.cn/github_assets/.../esp-idf-v5.5.4.zip`（1.83GB 含全 submodule）→ **3.4 MB/s，8 分钟**。
   - 副作用可控：该 zip 自带 `.git`，但解压后 `git describe` 会超时（28k 文件 mtime 全新、判 dirty 要 stat 全树）→ 放 `version.txt` 绕开，代价只是版本号带 `-dirty`。
2. **复用既有 `IDF_TOOLS_PATH`，两个 IDF 版本并存，而不是清掉旧的**
   - 本机原有官方 installer 装的 **v5.1.2**（编不了 P4）。选择保留 + 新版共用 `D:\esp32\Espressif` 工具目录：cmake/ninja/openocd/ccache/idf-python/idf-git 全部共享，只多下一套新版 riscv 工具链。
   - **代价（必须记住）**：机器级环境变量 `IDF_PATH` 仍指向 v5.1.2 ⇒ **任何 P4 操作前必须先 dot-source `tools/idf_shell.ps1`**，不能靠系统环境。这也是为什么把环境激活单独抽成一个脚本、而不是散在各处 `$env:` 赋值。
   - 备选（未采纳）：装到全新独立目录 → 干净但要重下 ~700MB 已有工具，且旧工程可能受环境变量切换影响。
3. **Python 下不动就换 curl 预取，而不是继续修 Python 的网络**
   - 修完证书（`SSL_CERT_FILE` 指 git 的 ca-bundle）后 Python TLS 仍对特定域名被切；同时 curl 对同一批 URL 全部正常。判断**这是链路对 SNI 的干扰、不是配置错**，继续在 Python 侧调是无底洞。
   - 于是从 IDF 自带 `tools/tools.json` 解析 url/size/sha256，curl 批量拉进 `dist/`，让 `idf_tools.py` 走"本地包已存在"分支（8 包 757MB / 100 秒）。**这个思路可复用于任何 idf_tools 下载失败的场景**（含日后升级 IDF、加新 target）。
4. **工程挪到 `workbench/esp32p4/p4_lcd`（全 ASCII 短路径），而不是留在 `workbench/_参考工程/`**

## 2026-07-27（十八）ESP-01S 双模块无线遥测桥：从方案评估到桌面收口 + 提交（`a5ee7f4` / `60c32a2` / `a941382`）

> 从 `CONTINUATION_GUIDE.md` §三 迁入的完整迭代史。**当前状态与剩余待办以真值源 [`workbench/天猛星主板平台/无线遥测_ESP01S链路.md`](../../../workbench/天猛星主板平台/无线遥测_ESP01S链路.md) 为准**，本条只留"怎么走到这一步"和被推翻的判断。

### 需求与架构取舍

用户要"小车脱离 USB 线在地上跑，PC 能实时读真实数据"。第一版评估（同日早些时候）判的是"车上一个 ESP + PC 用 WiFi socket 收"，并把**上位机脚本全部要重写**列为最大工作量坎。用户随后说他备了**两个** ESP-01S + 两个 CH340 → 改走**双模块透明串口桥**：车端 A=SoftAP、PC 端 B=STA，**PC 那头仍是 COM 口** ⇒ 现有 `.ps1` 零改动，那个坎直接消失。

**车做 AP 而不是 PC 做 AP** 的理由：车上电就自建网、不依赖 PC 先在线（车在场地上跑，反过来依赖 PC 是错的）；AP 的 IP 天然固定 `192.168.4.1`，STA 的发送目标永不变。**B 配静态 IP 而非 DHCP**：两边地址全硬编码、上电少一次握手。**只有 A 存 `SAVETRANSLINK`、B 不存**：`AT+SLEEP` 不持久化而 modem-sleep 让抖动差 4 倍 ⇒ B 每次上电都得发 AT，那就顺手用 `esp_pc_up.ps1` 全配一遍；车上没人能给 A 发 AT，所以 A 必须自动进透传。B 保持 AT 模式还能随时查 RSSI、且永不会陷进"只能 `+++` 才能救"的状态。

### 被实测推翻/纠正的判断（三条，留痕防再犯）

1. **"50Hz 遥测会明显丢"——错**。速率扫描实测 **0% 丢包一路顶到 177Hz**，而 177Hz 正是 115200 波特下 62 字节行的物理上限（62×10/115200=5.4ms/行）⇒ **WiFi 不是瓶颈，串口才是**。
2. **"延迟 avg 48.8ms"——一半是我自己的表**。采样循环里 `Start-Sleep -Milliseconds 3` 在 Windows 上实际睡 ~15.6ms，换紧凑轮询后同一链路读 31.3ms。（已入坑库）
3. **`esp_rssi_walk.ps1` 记成"另一条对话的产出"——错**，是本线自己写的；我看 `git status` 时误归因，提交前已改正。教训：并发工作树里**按内容/笔迹判归属，别按"我印象里没写过"判**。

### 关键发现：`tail 0` —— ESP 开机日志会被 MCU 当命令执行

`ESP.TXD → MCU.PA11` 的接法下，ESP 每次上电吐的 boot 日志会灌进 `car.c` 的 `poll_uart()/run_cmd()`，而它**无帧头**（遇 `\r\n` 就把首字符当命令）。抓 650 字节**原始字节**在 PC 上回放解析逻辑：22 行会被当命令，其中 **`tail 0` / `tail 4` / `tail 0` 三行首字符正好是 `t`（设定目标值）**，`parse_int(" 0")` 遇空格即返回 0 ⇒ **每次 ESP 上电必静默执行 3 次「改目标 + reset_all_pid()」**。真车症状是"跑着突然停/目标莫名归零"，凶手在第三方模块的启动日志里，查电机/编码器/PID 永远查不到。

**修法选型**：没选"加 `#` 帧头"（要同步改 6 个发送脚本），选**严格格式门 `cmd_format_ok`（只接受 `<字母>[-][数字]`）+ 上电静默窗 `CMD_MUTE_MS` + 遥测 `rej=` 计数**——因为现有脚本发的都是 `m3/t900/p150/z/?`，格式门**向后 100% 兼容、零 blast radius**，而那 22 行 boot 日志逐行都被拒（每行都含空格或多余字母）。固件仍接受可选 `#` 前缀，想再加固随时可切。
