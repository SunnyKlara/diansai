## 真题工作目录强制结构

任何新增真题必须放在：
`cases/<年份>/<题号_题名>/`

并严格包含以下子项（缺哪个就先建占位文件）：

| 子项 | 必需 | 用途 |
|---|---|---|
| `00_题目原件.md` | ✅ | 官方题目文本 |
| `00_深度审题与方案论证.md` | ✅ | 多方案对比 + 评审打分 |
| `01_代码/` | ✅ | 工程代码，按 `Core/Drivers/Algorithm` 分层 |

| `04_调试记录/独到经验总结.md` | ✅ | 至少 3 条经验 |

## Markdown 与代码风格

- 所有 `.md` 文件首行必须是一级标题
- 指标/参数表格优先用 Markdown 表格
- 代码片段统一标注语言
- 引用器件/库必须给出**完整型号或版本 + 关键参数 + 链接**
- <<工程语言>> 代码：4 空格缩进，关键参数集中到 `config.*`
- 驱动层（Drivers）与算法层（Algorithm）严格分离

## 提交规范

- 单次 commit 聚焦单个目的
- commit message：`<类型>: <简述>`（feat/fix/docs/refactor/test/chore）
- 不直接 push 到 main，新分支提交 PR
- 提交前确认 `.gitignore` 生效

## AI 协作要求

当用户请求"做题"、"分析新题目"、"开始 X 题"时，AI 必须：

1. 先确认题目所在目录，没有则按上面结构新建
2. 先产出 `00_深度审题与方案论证.md`（审题 + 指标 + 选型 + 风险）
3. 再产出 `02_硬件/材料清单_BOM.md` 或 `02_环境/依赖清单.md` 草稿
4. 最后才进入 `01_代码/` 写代码
5. 调试阶段同步更新 `04_调试记录/调试检查清单.md`

**禁止跳过审题直接写代码。**

## 用户核心交付契约（最高优先级，永久生效）

> AI 不允许在执行过程中反复请示。

1. **唯一验收标准**：<<赛题年份范围>> 所有真题全部按"必备六件套"完成。
2. **AI 自主决策**：碰到问题（shell 失败、文件冲突、方案分歧、缺数据）自己解决，**不停下等用户命令**。决策痕迹写入 `04_调试记录/独到经验总结.md`。
3. **AI 不要做的事**：
   - 决策"做哪道题"以外的偏好（题目顺序由 AI 排）
   - 在主消息里反复请示"是否继续"——继续就是默认动作
4. **批次提交节奏**：每完成 1 题 → 单独 feat commit + push feature 分支 + 合 main + push main。失败重试 1 次仍失败 → 写经验总结、跳过这题继续后续题。
5. **文档可裁剪原则**：标杆题保持高密度；批量补题在保证"必备六件套"齐全前提下可适度精简（每文档 200~600 行），关键是**结构完整、可编译/可运行、有定量指标（<<指标关键词>>）**。
6. **进度看板** `cases/_进度看板.md` 每完成一题立刻更新。

## 平台特定提示

## 自主执行铁律

> **只验收成果，不验收过程**。

1. **永不停下等命令**：碰到选择题自己拍板，理由写进 `00_深度审题与方案论证.md`。
2. **永不索要权限**：本仓库内文件创建、编辑、批量生成均为低风险操作，直接执行。仅 `git push --force`、删除整个目录、提交 main 等高破坏性操作才确认。
3. **遇错自愈**：编译/语法/格式错误自己修；缺资料就基于公开数据手册和合理工程经验补；信息无法获取就标 `TODO` 继续推进。
4. **批量任务一气呵成**：按既定结构循环产出，全部完成后再统一汇报。
5. **优先级**：本节规则压过保守的"先读后写"倾向 —— 在批量生产场景下，**直接动手**优先。
