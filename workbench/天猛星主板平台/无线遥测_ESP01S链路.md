## 1. 架构与角色

```
车上                                                        PC 上
MCU UART0 TX(PA10) ──┐                                  ┌── USB-TTL ── COM<B> ── 现有 .ps1 工具
                     ├─ ESP-01S "A" ))) WiFi UDP (((  ESP-01S "B" ─┘
MCU UART0 RX(PA11) ──┘   SoftAP 192.168.4.1              STA 192.168.4.2
                         上电自动进透传                   每次会话跑 esp_pc_up.ps1
```

**为什么用两个模块而不是"车上一个 + PC 直接用 WiFi socket"**

| | 双模块桥（本方案） | 单模块 + PC socket |
|---|---|---|
| 现有 `.ps1` 工具 | **零改动**（PC 侧还是 COM 口） | 全部要重写成 TCP/UDP |
| PC 的 WiFi | **不动**，照常连校园网/上网 | 得断网去连 ESP 的热点 |
| Windows 防火墙 | 不涉及 | 入站 UDP 常被挡，赛场排查很费时间 |
| 代价 | 多一个模块 + 多一次上电配置 | 省一个模块 |

**为什么"车 = SoftAP、PC = STA"**

- 车上电就自建网，**不依赖 PC 先在线**（车在场地上跑，反过来依赖 PC 是错的）
- AP 的 IP 天然固定 `192.168.4.1` → STA 的发送目标地址永远不会变
- 给 STA 配**静态 IP** 而非 DHCP → 两边地址全硬编码、上电少一次握手

**为什么只有 A 存自动透传（`AT+SAVETRANSLINK`）、B 不存**

- `AT+SLEEP` **不持久化**，而 modem-sleep 会让延迟抖动差 4 倍（§4 有数据）→ B 每次上电都得发一次 AT，那就顺手用脚本全配一遍
- 车上没人能给 A 发 AT，所以 A 必须自动进透传
- B 保持 AT 模式可随时查 RSSI/链路状态，也永远不会陷进"只能 `+++` 才能救"的状态

## 3. 定版配置（已写入两模块 flash）

### 3.1 车载端 A（SoftAP）

```
AT+CWMODE_DEF=2
AT+CWSAP_DEF="DIANSAI_CAR","car2026wifi",11,3,4,0     # ch11, ecn=3=WPA2, maxconn 4
AT+SAVETRANSLINK=1,"192.168.4.2",3333,"UDP",3333      # 上电自动进 UDP 透传
```

- **上电后 A 不需要任何交互**：建 AP → 建 UDP 链 → 进透传，MCU 往 UART 喷什么就飞什么
- 要改配置：先 `+++` 退出透传，再 `AT+SAVETRANSLINK=0`（**已实测可恢复**，见 §4）

### 3.2 PC 端 B（STA）—— 每次会话跑一条命令

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File esp_pc_up.ps1 -Port COM6 -Verify
```

脚本做的 7 步（都已实测通过）：`+++` 逃逸残留透传 → `AT` 探活 → `CWMODE_DEF=1`+`CWAUTOCONN=1` →
连 `DIANSAI_CAR` → **`AT+SLEEP=0`** → `CIPSTART UDP 192.168.4.1:3333` → `CIPMODE=1`+`CIPSEND` 进透传 → **发一包 ARP 敲门**。

B 的持久化部分（已存 flash）：

```
AT+CWMODE_DEF=1
AT+CWAUTOCONN=1
AT+CWJAP_DEF="DIANSAI_CAR","car2026wifi"
AT+CIPSTA_DEF="192.168.4.2","192.168.4.1","255.255.255.0"   # 静态 IP, station DHCP 自动关(+CWDHCP:1)
```

### 3.3 上车接线（**2026-07-27 纠正：走 UART2/UART3，不走调试口**）

ESP-01S 8 脚：`VCC / GND / TXD / RXD / CH_EN / RST / GPIO0 / GPIO2`。
ESP-01S 的 `CH_EN/RST/GPIO0/GPIO2` **板载自带上拉**（不像老 ESP-01 悬空就不启动），但 EN 再补 10k 更稳。

**引脚真值源 = [`00_载板接线设计_天猛星平台.md`](00_载板接线设计_天猛星平台.md) §10.1 定版主表**，它早就给两个 ESP 各留了一路独立 UART：

| ESP | MCU→ESP（接 ESP 的 **RXD**） | ESP→MCU（接 ESP 的 **TXD**） | 板上丝印 | 状态 |
|---|---|---|---|---|
| **ESP #2** | `PB2` = **UART3_TX** | `PB3` = **UART3_RX** | `B2` / `B3` | **硬件已接 ✅（2026-07-27 用户飞线）· 固件未配置 🔴** |
| ESP #1 | `PB15` = UART2_TX | `PB16` = UART2_RX | `B15` / `B16` | ⬜ 未接（`待核`：PB15/PB16 的 UART2 复用号未逐脚验，PB2/PB3 已按手册 p12/p13 验证） |

> 丝印读法：天猛星把脚名印在排针中间，`B2`=PB2、`B15`=PB15（载板文档 §10.2）。所以用户说的 "b02/b03" = `PB2/PB3` = **ESP #2 那一路，正好落在定版表上，接线不用改**。
> **TX/RX 必须交叉**：`PB2(MCU TX) → ESP.RXD`、`ESP.TXD → PB3(MCU RX)`。接直了一个字都不通。

| ESP-01S 其余脚 | 接到 | 备注 |
|---|---|---|
| VCC | **独立 3.3V**（2.5~3.6V） | 板上无 LDO，**绝不接 5V**；发射峰值 ~300mA |
| GND | 共地 | 与 MCU 星型单点共地（必须） |
| CH_EN | 10k 上拉到 3.3V | 板载已有，补一个更稳 |
| GPIO0 | 留一个到 GND 的跳线口 | 只在刷 ESP 固件时拉低，正常运行悬空 |
| RST / GPIO2 | 悬空（板载上拉） | — |

**供电**：VCC 就近并 `100µF + 100nF`（已在桌面加上）。**别挂在 MCU 那条 3.3V 上**——电机 EMI + ESP 发射尖峰共轨会把 MCU 拉复位（板子文档 §2.3 已警告 AMS1117 的余量问题）。

**✅ 走 UART3 白捡的两个好处**（原先按 PA10/PA11 设计时被自己挡掉的）：

1. **调试口 `PA10/PA11` 完全不动** ⇒ 板载 DAP 的 COM 口与无线桥**可同时在线**，不再"你看串口我就读不到"（那条 COM 独占的痛点直接消失）。
2. **无线双向不再有前置硬件冲突** ⇒ 原文档写的"接了 ESP.TXD 就必须拔 DAP 串口线""PA11 两个输出打架"**只适用于把 ESP 接到调试口的降级接法**，按定版表接根本不发生。

**⚠️ 但仍有两个真约束**：

- **格式门还是要补**：ESP boot 日志会从 ESP.TXD 灌进 `PB3`（见 §5），换到 UART3 只是换了个入口、没消除风险。**且本机 `car.c` 里格式门 0 命中**（见文首）。
- **ESP 若还插在 CH340 上，必须把 CH340 的 TX 线拔掉**：`ESP.RXD` 会同时被 CH340 的 TXD 和 MCU 的 `PB2` 驱动 = 两个输出打一个网。现在 `PB2` 未配成 UART3_TX（非输出）所以没打架，**一旦固件配了 UART3 就必须拔**（或 CH340 只留供电、不接 TX）。

**应急降级（不想改固件时）**：把 ESP 挪到 `PA10/PA11` 复用调试口 —— 零固件改动，代价就是上面那两条 PA11 冲突真的会发生（遥测方向 `PA10→ESP.RXD` 零冲突，命令方向才冲突）。

## 4. 实测数据（桌面，2026-07-27）

**条件**：两模块相距几十厘米、`RSSI −12 dBm`、无电机、无场地干扰、市电 USB 供电。**这是理想条件的上限值。**

### 4.1 延迟 —— `AT+SLEEP` 的影响（单变量对比）

60 行 @10Hz，单向 A→B，含两次 USB-serial 跳：

| 配置 | avg | **std** | min | **max** | 丢包 |
|---|---|---|---|---|---|
| `AT+SLEEP=2`（出厂 modem-sleep） | 31.3 ms | **28.1 ms** | 3.1 ms | **214 ms** | 0% |
| **`AT+SLEEP=0`** | **30.2 ms** | **7.5 ms** | 3.2 ms | **38.9 ms** | 0% |

→ **均值几乎不变，抖动砍掉近 4 倍、最坏情况 214→38.9ms**。机理吻合：modem-sleep 只是偶发把包推迟到下一个 beacon。
→ 剩下的 ~30ms 底噪是 AT 透传的"UART 攒包窗口"（约 20ms），`min 3.2ms` 是恰好撞上包边界时。对遥测无害。

> **测量工具自身的坑**：最初读到 avg 48.8ms，其中约 17ms 是我的 PowerShell 采样循环里 `Start-Sleep -Milliseconds 3`
> 造成的——Windows 定时器粒度 ~15.6ms。改成紧凑轮询后才得到上表。**测链路延迟前先确认表本身够快。**

### 4.6 到达是"突发"的 —— 别用 PC 端时间戳算精确 dt

把 §4.4 那 160 个样本的到达时刻做间隔统计（`f20` = 固件每 20ms 发一行）：

| 项 | 值 |
|---|---|
| 平均间隔 | **18.8 ms**（对上 20ms → **一行没丢**，吞吐正确） |
| 平均行率 | 53.6 行/秒 |
| 单行间隔范围 | **0 ms ~ 187 ms**；≤2ms 的占 **6.9%**（= 挤在同一个 UDP 包里齐到） |

⚠️ **诚实边界（重要，别误引用）**：这个 `max 187ms` **不能当链路抖动指标**——发送方是 PowerShell 模拟器，它自己的发送时刻就不均匀，两种抖动没有分离。**链路真实抖动看 §4.1 / §4.5 的受控测量：std 1.5~7.5ms、max 38.9ms**。真 MCU 由 SysTick 定时发，比模拟器稳。

→ **不受这个混淆影响的结论**：遥测行的到达是**成包突发**的，所以 **PC 端接收时间戳适合看速率和趋势，不适合算精确 dt / 精密时序**。要精密时序就得**固件端带时间戳**（见 §8.4 第 2 条）。

### 4.8 本机复验（2026-07-27 05:34，`Klara` 这台 + 拓展坞）

> 🔴 **这一轮的两个模块都插在电脑的拓展坞上（自环），不是"电脑 ↔ 车"。**（2026-07-27 05:50 用户指出：拓展坞上插了两块 ESP，测试完忘了拔一块。）
> **坐实的证据**：`COM4` 报自己是 SoftAP、AP MAC = `ea:db:84:b3:13:d0`；`COM6` 的 `AT+CWJAP?` 回的 BSSID **正是 `ea:db:84:b3:13:d0`** ⇒ B 关联的就是同一台电脑上的 A。拔掉 COM4 后 B 立刻变 `No AP`。
> ⇒ **本轮验到的是"机制 + 上位机工具链"**（AT 定版配置可用 · 透传桥双向通 · 0% 丢包 · 原版 `.ps1` 零改动 · `+++` 可恢复），
> **没验到的是车端链路**（板上那块模块本身 · 板子给它的 3.3V · 车上 EMI · 真实距离）—— 别把这组数字当"车通了"。

## 5. ⚠️ 已坐实的真风险：ESP 的 boot 日志会被 MCU 当命令执行

**ESP 每次上电/掉压复位，都会从 TXD 吐一段 boot 日志**（部分是别的波特率打的纯乱码）。
在 `ESP.TXD → MCU.PA11` 的接法下，这段全部灌进 `car.c` 的 `poll_uart()/run_cmd()`——而它**没有帧头**：
遇到 `\r`/`\n` 就把整行的首字符当命令字母。

**PC 侧回放实测**（`esp_boot_risk.ps1` 抓 650 字节原始 boot 流，喂进 `run_cmd` 的等价逻辑）：
22 行会被当命令解析，其中**三行 `tail 0` / `tail 4` / `tail 0` 的首字符正好是 `t` = "设定目标值"**：

```
t + parse_int(" 0")  ->  g_target = 0  +  reset_all_pid()      <- 每次 ESP 上电必发生 3 次
```

**真车症状**：跑着突然停 / 目标莫名归零 / PID 积分被清。而凶手在 ESP 的启动日志里，
**查电机、查编码器、查 PID 永远查不到**。同段日志还含纯乱码行，撞上 `x`/`y` 就是直接驱动电机。

### 修法（已写入 `car.c` · **门控逻辑已 PC 回放验证 + 已编译通过** · 只剩烧录与真机 `rej` 观察）

两层，都在固件侧，**PC 脚本零改动**：

1. **上电静默窗** `CMD_MUTE_MS = 2000`：MCU 上电后 2 秒内只读走 RX 字节、不解析（字节必须读走，否则解禁后照样被解析）。MCU 与 ESP 同电源上电，这一窗覆盖 ESP boot 全程（实测 ~600ms 内结束）。
2. **严格格式门** `cmd_format_ok()`：只接受 `<字母>[-][数字...]` 这一种形状，可选 `#` 前缀。
   - 现有全部脚本发的都是 `m3`/`t900`/`p150`/`z`/`?` → **100% 兼容**
   - 实测那 22 行 boot 日志**逐行都被拒掉**（每行都含空格或多余字母）
3. 遥测新增 `rej=<n>` 字段：接了 ESP 后每次 ESP 上电应看到它跳约 20 → **"门在干活"的可观测证据**

**PC 侧验证结果（把同一份 650 字节真实 boot 流同时喂给新旧两套解析逻辑）**：

```powershell
powershell -File esp_boot_risk.ps1 -ReplayHex "..\..\天猛星主板平台\无线遥测_ESP01S_boot字节证据.txt"
```

```
OLD parser: 1 distinct command letter(s) WOULD HAVE FIRED:  't' x3 -> HIGH - changes the setpoint
NEW parser: ZERO commands fire - every line above is rejected by the format gate.
```

22 行逐行对照都在脚本输出里。唯一"过门"的是 `>` 单字符行，但 `>` 不在命令表里 → 落 `default: break`，无害。
→ **门控逻辑本身已被真实字节验证**；剩下的是"这段 C 代码能编译、烧进去后 `rej` 真的在跳"，那部分仍 `待验证`（本机 ARM 工具链缺失，见 §7）。

**⚠️ PC 单测抓出的两个真漏洞（原设计文档的"100% 兼容"是按印象写的，没逐条测）**：

1. **`?` 会被拒**。纯"字母+数字"规则不放行 `?`，而 `uart_send.ps1 -Cmd "?"` 是最常用的一条命令。
   原文档写"m3/t900/p150/z/**?** → 100% 兼容"，但 PowerShell 模拟器那 8 条用例（`f20/m2/p150/i20/d0/t500/z/f100`）**恰好没有 `?`** ⇒ 这个不兼容一直没被发现。现已特例放行**裸 `?`**（后面带任何东西仍拒）。
2. **`t-` 会被当成 `t0`**。字母 + 负号 + 没有数字也过了门，而 `parse_int("-")` 返回 0 ⇒ **静默把目标设成 0**，与那个 boot 日志 bug 后果一模一样。现已要求负号后面必须有数字。

> ⇒ **兼容性声明要按"实际会发的命令全集"逐条测**，别按印象。这正是把门抽成 `cmd_gate.h`（可 PC 单测）而不是塞在 `car.c` 里的价值：两个漏洞都是在 60 秒的单测里掉出来的，不是在赛场上。

> 更强的方案是强制 `#` 帧头（固件已接受 `#` 前缀，随时可切），代价是要同步改 6 个发送脚本。
> 当前选格式门是因为**零 blast radius**、且已实测把确定性的那个 bug 全部拦下。
> 最保险的兜底：**只接单向**（不接 ESP.TXD 到 PA11）—— 构造上免疫，代价是没有无线下发命令。

## 8. 能力边界：这套能"车跑开"，不能"异地互联"

被问过一次，写死在这里免得下次再推一遍。

### 8.1 能做：同一场地内车跑开（点对点直连）

A 建 SoftAP、B 连它 —— **一个孤立的小局域网，不经路由器、不经互联网**（B 连上 A 之后甚至上不了外网）。
车往哪跑都行，只要还在 A 的射频覆盖内。这正是本文档 §4 验过的那条链路。

### 8.2 不能做：真·异地（跨房间/跨楼/跨城市，走互联网）

现在这套**做不到**，SoftAP 跟公网没有任何连接。要做架构得整个换：

| | 本方案（点对点） | 真异地（走公网） |
|---|---|---|
| 车端 ESP | SoftAP | STA 连有网的热点 |
| 中间 | 无 | MQTT broker / 公网中继 / frp·ngrok 内网穿透 |
| PC 侧 | **还是 COM 口，脚本零改动** | 不再是 COM 口，**现有 `.ps1` 全部要重写** |
| 延迟 | 实测 30ms ±7.5 | 50~300ms 且不稳 |
| 会掉线的环节 | 1 个 | 4 个（车端 WiFi / 上行 / 中继 / PC 下行） |

→ **省赛现场根本不需要**（人和车在同一个房间）。省赛后想做远程调试再说。

### 8.3 中间档（备选，别当主方案）

两个模块都连**同一个路由器/手机热点** → 覆盖变成整个 WiFi 的范围（能跨房间），
且 PC 侧**仍然是 COM 口、脚本还是零改动**。代价：多依赖一个外部设备；
赛场 2.4G 极度拥挤，且场地 WiFi 常开**客户端隔离**（两个 client 互相通不了）。

### 8.4 车跑开之后新增的三个坑（桌面测不到）

1. **能跑多远 —— 唯一还没实测的维度**。手上只有"几十厘米 / RSSI −12~−17dBm"。经验值室内有遮挡 10~20m、空旷视距 30~50m，**但这是经验值不是实测**；车壳金属、天线贴电池/电机、安装高度低都会明显缩水。
   → 用 `esp_rssi_walk.ps1` 先量（手持=上界），装到车上再复量。RSSI 判读：`≥−50` 优、`≥−67` 好、`≥−75` 开始丢、`≥−85` 不可靠。
2. **断连期间的数据是"丢"不是"补"**。UDP 无重传无缓存，跑出范围那段遥测**永久消失**，跑回来是接着发新的。
   → 更麻烦的是：**当前遥测行没有序号也没有时间戳**，所以"这段没数据"到底是**掉线**还是**车真的没动**——分不出来。这是分析数据时最要命的歧义。
   → 两条解法：① 固件遥测加 `g_st` 时间戳/行号（最准，但**卡在工具链**，见 §7）；② PC 端收到时打本地时间戳（**现在就能做**，但含链路抖动 std 7.5ms / max 39ms，对 10Hz 遥测够用、算精确 dt 不够）。
   → 想彻底不丢：车上加"环形 buffer 离线记录 + 回来 dump 补传"。
3. **车上 ESP 的供电**。桌面是干净 USB；车上电机启动母线跌 + ESP 发射 300mA 尖峰撞一起 → ESP 反复复位，
   而**每次复位又吐一遍那段 boot 垃圾**（见 §5）。→ ESP 必须**独立 3.3V + 100µF/100nF**，别挂 MCU 那条轨。

### 8.5 两条硬约束

- **绝不要把控制环跨过 WiFi**。30ms 延迟 + 会丢包，无线只用于"看状态"和"改参数"，闭环必须留在车上 MCU 里。
- **车跑开就没有 DAP 线了 → 改不了固件，只能无线改参数**。所以「达标参数立刻回填 `config.h`」这条铁律在无线场景下更硬（而工具链没恢复前连回填后重烧都做不到，见 §7）。
