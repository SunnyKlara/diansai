## 2026-07-24  M-事故  MSPM0 内核死锁(lockup) → 调试口 MEM-AP 消失 → 工厂复位救砖（真机 ✅ 已恢复）
- 现象链：LCD demo 本跑得好好的（计数跳）→ AI **连续快速反复烧录/openocd 连接压测** → 之后烧录一律报 `Error: Could not find MEM-AP to control the core`（DP 能读 `DPIDR 0x6ba02477`，但 AP 消失）→ PB22 不闪、屏黑、**断电重启也不恢复**。
- **根因（实锤）**：内核陷入 **double fault → lockup**（工厂复位过程刷出 `clearing lockup after double fault`）。触发链：连续快烧中某次 `program` 擦了 flash 又被打断 / 反复 halt 打断运行 → flash 留下**无效镜像** → 上电执行非法向量 → HardFault→双故障→**内核死锁** → 死锁的核**同时把 SWD 的 MEM-AP 门控掉** → 既连不上也跑不了；且无效/空白 flash 使**每次上电立刻再死锁**（所以断电重启无效）。
- **没用的救法**：① 按住 RST 再连（松手时机救不了）；② 单独 `mspm0_factory_reset` 成功后**再单独** `program`（两条命令之间核又死锁）；③ 单独 `program` + 点 RST（program 只 examine 一次，抓不到窗口）。
- **✅ 成功救法（可复现，记死这条）**：把"工厂复位 + 写固件 + 复位运行"**塞进同一条 openocd 命令**，中间不给它再死锁的机会：
  ```powershell
  openocd -s C:/ti/xpack-openocd-0.12.0-7/openocd/scripts -f interface/cmsis-dap.cfg -c "adapter speed 500" -f target/ti_mspm0.cfg -c "init" -c "mspm0_factory_reset" -c "flash write_image erase gpio_toggle_output.out" -c "verify_image gpio_toggle_output.out" -c "reset run" -c "shutdown"
  ```
  操作：回车后**"哒哒哒"连续点按板子 RST 键**；**一看到 `Factory reset success!` 立刻停手**（别在写 flash 时再复位）；随后自动 `wrote 11064 bytes` + `verified` + `reset run`。原理：工厂复位(DSSM 命令 0x020a，走 SECAP/AP2，不需要 MEM-AP)解锁并 halt 住内核 → 趁 AP 还开着一口气写入**有效**固件 → 复位跑新固件，不再死锁。`mspm0_factory_reset` 需要真复位 NRST，本 DAP 没接复位线 → 靠**手点 RST 键**提供。
- **烧后小 quirk（非故障）**：`reset run` 软复位后屏黑（背光亮）；**手动按一下 RST 硬复位 → 正常显示**。→ 烧完按一次 RST 做干净冷启动即可。
- **预防（铁律）**：① **绝不连续快烧 / 反复 halt / 中途打断 program**（今天死锁的根）——节奏永远是"烧一次→看现象→改→再烧"；② 遇 `Could not find MEM-AP` + 核不跑 + 断电无效 = 死锁，用上面那条组合命令 + 点 RST 救；③ 烧完按一次 RST 冷启动再看现象。

## 2026-07-24  M-串口  car 加 UART0 调试打印 + DAP VCOM 读通（真机 ✅）

- **目标**：小车要串口 log。天猛星"默认调试串口"= **UART0**，丝印 `A10`/`A11`（§10.1）：**PA10=UART0_TX、PA11=UART0_RX**，接 DAP 的 VCOM。
- **接线（交叉！）**：天猛星 `PA10(TX)`→DAP `RX`、`PA11(RX)`→DAP `TX`、`GND` 共地。DAP 的 VCOM 在本机枚举为 **COM30**（设备名"USB 串行设备"）。
- **代码**：`car.syscfg` 加 UART 模块（`$name=DBG_UART`→UART0，`rxPin=PA11`/`txPin=PA10`，115200，enableFIFO）；新增 `uart_dbg.c/.h`（`DL_UART_transmitDataBlocking` 逐字节阻塞发，不用 printf 省 flash）；`car.c` 每次动作切换打一行 `[car] #n NAME M1=.. M2=..`。固件 text 12784→13504B。
- **真机验证**：openocd `reset run` 后，PowerShell 开 COM30@115200 读 6s，收到 `[car] #14 TURN M1=40 M2=-40` / `#16 REVERSE M1=-40 M2=-40` … 连续正常 → **串口通路 + 波特率 + 接线方向全对**。开头几个字节乱码 = 开串口瞬间抓到半个字节，正常，丢弃即可。
- **API 名坑**：发送是 `DL_UART_transmitDataBlocking(inst, byte)`（**不带 Main**）；接收是 `DL_UART_receiveDataBlocking`。而填 FIFO 的是 `DL_UART_Main_fillTXFIFO`（带 Main）。命名不统一，先 grep `dl_uart.h` 确认再用。
- **🔴 烧录 verify 坑**：`program car.out verify reset` 在 verify 阶段报 `timed out while waiting for target halted` + `error executing cortex_m crc algorithm` → **Verify Failed 且不 reset**。根因：verify 用 CRC 要 halt CPU 跑校验程序，@1000kHz SWD 时序抖动偶发超时。**flash 其实已写入成功（Programming Finished）**，不是固件坏。
  - **解法**：烧录降速 **500** + **去掉 verify**：`program car.out reset exit`（写完直接复位跑）。开发调试看 log/看现象即可判对错，不必每次 CRC 校验。或烧后手动按 RST。

### 二、标准（阈值不是拍的，是从 L1 判据反算 + 误差量化）
- `imu_axis.ps1 -Step L1` 的判据是"竖直轴 ≥900mg 且**其余轴 ≤250mg**"，后者更紧：`asin(0.25)≈14.5°` ⇒ **14° 是"能定轴"的底线**。

- ⇒ 三档：**绿环 ≤2°(优) / 黄环 ≤5°(良) / 橙环 ≤14°(底线)**；`|a|` 出 850~1150mg 带则显示 `HOLD STILL` 不给判定（在动/振动时倾角不可信）。

### 一、定轴到底在定什么（把问题说清才发现原方案是笨的）
IMU 有自己固定在芯片上的 X/Y/Z；车有自己的"前/左/上"。定轴 = 找出**车按行驶姿态摆好时，IMU 的哪个方向指天**，以及**左转在该方向上读正还是读负**。这是**机械安装事实**，不在任何数据手册或代码里，只能靠"在真实姿态下量一次重力"得到。
⇒ 所以"AI 能不能自己定"的准确答案是：**算法上完全能自动定；唯一必须由人给的是"此刻的姿态就是以后要跑的姿态"这个语义事实**——传感器测得出"现在朝哪"，测不出"这个朝向是不是你以后要跑的朝向"。

### 二、改动：`挑最近轴 + 循环置换` → `投影到测得的天顶方向`（主路径）

### 1. 烧录：写入成功，但 verify 报了一个**假的** FAIL

```
wrote 33208 bytes from file gcc/car.out in 87.719704s (0.370 KiB/s)
Error: timed out while waiting for target halted        <- 已知且无害(CRC helper)
Error: checksum mismatch - attempting binary compare
diff 0 address 0x00000004. Was 0x05 instead of 0x6d
… 共 10 处
RESULT: FAIL - flash content does NOT match the binary (10 differing byte(s)).
```

`wrote N` 的 N **正好等于** `arm-none-eabi-size` 的 text+data（33040+168=33208）⇒ 写入量对。
串口读 6s **零字节** ⇒ 当时 app 没在跑，看起来确实像"烧坏了"。

**但没有立刻重烧**（脚本当时建议 Re-flash，而那正撞"绝不连续快烧"禁忌）。先做了两件事：

**① 看失败模式，不看结论**：10 个坏字节落在**两个 8 字节对齐的字**（`0x0000`、`0x5800`）。
随机 SWD 误码不会这么巧（4151 个字里恰好两个、且都对齐）⇒ 不是信号质量问题，别去降速。
**② 逻辑上还有个矛盾**：扇区若被擦过，那两个字不可能读回**旧值**（擦后是 0xFF，旧值回不来）⇒ 怀疑**读回**有问题。

**只读会话取证**（`openocd … -c init -c "mdw …"`，不擦不写）：

| 地址 | 实读 | 文件期望 | verify 报的 "was" |
|---|---|---|---|
| `0x0` | `20208000 00005a6d` | 复位向量 `0x5a6d` ✅ | 说是 `0x5805` ❌ |
| `0x5800` | `00008050 00001804` | `50 80 00 00 / 04 18 00 00` ✅ | 说是 `fe e7 c0 46 / 15 48 16 4b` ❌ |
| `0x5a68` | `46c0e7fe 4b164815` | — | **verify 报的那串在这儿** |

⇒ **flash 内容完全正确**。verify 报的"was"那 8 字节，是**旧镜像 Reset_Handler 的字节**
（新镜像里同一段启动码搬到了 `0x5a68`，所以模式一模一样）。
**结论：`verify_image` 回落的 host-side 字节比对读到了擦除前的陈旧数据**——最合理的机制是 flash 预取/cache 里
还留着**复位那一刻 CPU 取过的两条线**（`0x0` 的向量表 + Reset_Handler 那条），erase/write 没让它失效，
而 CRC helper 超时又把目标留在了异常状态。两条 cache line = 恰好 2×8 字节，与现象吻合。

> ⚠️ **这是一种和文档里已记的假失败不同的新种类**：已记的是"CRC helper 超时"，
> 这次是**字节比对本身读到陈旧数据** ⇒ **看到 `diff` 也不能直接判写坏**。
> **正确处置 = 先用只读会话 `mdw` 复核那几个地址**（几秒钟），再决定要不要重烧。
> 按脚本原来的建议直接 Re-flash，就会白烧一次 87 秒并额外承担一次 brick 风险。

## 2026-07-27  🎉 M-无线打通  **PC ↔ 车 无线遥测 + 无线下发命令 全部真机通了**（靠新增的 `b<秒>` AT 桥接解开死局）

**死局**：车载 ESP 的串口只接 MCU 的 `PB2/PB3`，**板上没有第二个串口座、模块也拔不下来**（与电脑端那两块不是同一型/不可互换）⇒ PC 永远碰不到它，而**没配过的模块永远不会转发数据**。

**解法 = 固件加 `b<秒>` AT 桥接**（`car.c` `bridge_pump()`）：桥接期内把有线口(UART0/DAP) 与 UART3 **原样字节对接**，不解析命令、不打遥测；**超时自动退出**（不用逃逸序列——桥接期每个字节都要原样转发，任何"魔法序列"都会和 ESP 自己的 `+++` 抢语义）。进入前先 `stop_all()`。
镜像 **`text 33688 + data 168 = 33856 字节`**（新烧录判据）。

**桥接一通就问出了车端是什么**（此前完全未知）：AT `1.7.4.0` / SDK `3.0.5-dev`（**与另两块同版**）· `CWMODE=2` · SSID `AI-THINKER_B835BD` · AP MAC `86:0d:8e:b8:35:bd` ⇒ **出厂态**，坐实"它永远不会转发"。

**⚠️ 角色被迫反转（与原设计相反，取舍要记住）**：原设计 = 车端 SoftAP / PC 端 STA（车不依赖 PC 先在线）。
但**已配好 `SAVETRANSLINK` 的模块 A 现在插在电脑上且拔不动车端那块** ⇒ 改成 **车端 = STA、PC 端 = AP(A 不动一个字)**。
车端配置（经桥接下发，全部持久化）：

```
AT+CWMODE_DEF=1
AT+CWAUTOCONN=1
AT+CIPSTA_DEF="192.168.4.2","192.168.4.1","255.255.255.0"
AT+CWJAP_DEF="DIANSAI_CAR","car2026wifi"
AT+SLEEP=0                                            # 不持久, 每次上电想要低抖动得重发
AT+SAVETRANSLINK=1,"192.168.4.1",3333,"UDP",3333      # 上电自动进 UDP 透传
```

**代价（诚实标注）**：车端是 STA ⇒ **依赖 PC 端那块 AP 先在线**。赛场笔记本一般先开机，可接受；要翻回"车端当 AP"随时能做——**有了 `b` 桥接，改配置不用再拆车**。
