## 1. 量化：一道电赛车题，AI 协作到底花了多少

| 指标 | 实测值（从会话记录统计） |
|---|---|
| 日历跨度 | 2026-07-09 07:44 → 07-11 17:28（**3 天**） |
| **真正活跃工时** | **13 个活跃小时**（07-09 两段 / 07-10 四段 / 07-11 七段） |
| 会话记录条数 | 4245 条（含 686 条 reasoning + 315 条对人汇报 + 389 次工具调用） |
| **上下文压缩次数** | **3 次**（07-10 10:25、07-11 05:49、07-11 07:52）≈ 每 4 活跃小时一次 |
| 人类发言 | **75 条 / 约 1.16 万字**（平均一条 155 字，很多只有"已居中""左侧好了"） |
| 编译 `build.ps1` | **41 次** |
| 烧录 `flash.ps1` | **31 次** |
| **串口交互 `serial_console.py`** | **104 次** ← 最高频 |
| OpenOCD 调试/探测 | 22 次（+ `detect_probe.py` 10 次） |
| SysConfig 静态检查 | 19 次 |
| **烧录间隔中位数** | **5.1 分钟**（同时段内 27 个间隔；最短 0.2 min = 失败重试，最长 24 min） |

**三个比例最值得记住**：

- **串口 : 烧录 ≈ 3.4 : 1** —— 每烧一次固件，围着它做 3~4 次串口观测/在线调参。**"能在线调的绝不重烧"**——这与我们的 `uart_send.ps1` / `tune_step.ps1` 路线一致，但他们把这个比例拉得更高。
- **编译 : 烧录 ≈ 1.3 : 1** —— 几乎"编译即烧录"，说明改动颗粒**很小**（不攒一堆改动再验）。
- **一个真机迭代 ≈ 5 分钟**。这是我们排赛中时间的基准：一个"改码→编译→烧录→串口验"的闭环 5 分钟，13 小时能做约 30 次固件迭代 + 100 次在线观测。**这就是"做完一道车题"的真实工作量刻度。**

> ⚠️ 我们的现实差距：我们不能像他们那样 5 分钟一次连续烧（本仓库禁忌 §D2：连续快烧/中途打断会把 MSPM0 怼进 double-fault 锁死，救砖要手点 RST）。**所以我们必须把"在线调参"的比例做得比他们更高**——运行时命令 (`m/t/p/i/d/w/e/f`) 已经是对的方向，赛中要继续往这上面靠。

## 2. Agent 每条汇报的**固定结构**（这是最该抄的东西）

翻 315 条会看到一个几乎不变的模板：

```
① 实测数字（不是"好了"，是 "误差 -26~+329 / 全量程 ±3500 ≈ 5%"）
② 判读（这些数字说明什么、是通过还是不通过）
③ 下一步 + 需要人做什么（精确到体位/位置/保持时间）
④ 回复口令（"然后回复我'白底好了'"）
```

真实例子（灰度标定阶段）：

> "居中结果通过：`lost` 始终为 0，误差主要在 -26 到 +329，相对于全量程 ±3500 只约 5%…**下一步确认左右符号：请站在车尾面向车头，把黑线移到灰度阵列的'小车左侧'约最外两颗探头下方，保持不动，然后回复'左侧好了'**。"

**为什么这条对我们特别关键**：我们踩过完全对应的坑——位置环手推刚度测试**连续 3 次拿不到干净数据**（用户离开 / 在进模式瞬间就推 / 位置保持模式静默没意识到窗口是活的）。他们的解法就是**把实验协议化**：AI 定义"站哪、放哪、保持多久、回什么口令"，人只需照做 + 回四个字。人类那 75 句里有 20 多句就是 `已居中` / `左侧好了` / `白底好了` / `已放回` / `重连完成` 这种口令。

**行动项（赛中直接用）**：凡是需要人配合的真机测试，AI 发起时必须给齐 **①放置/体位 ②保持时间 ③开始口令 ④结束口令**，并且**先留基线秒数**。

## 3. 烧录/链路失败的四步处理法（他们用无线 DAPLink，比我们更脆，处理更规范）

从会话记录里摘出的完整链条：

1. **先分类，不先改代码**："24MHz 写入后校验在 `0x1A18` 附近不一致，降到 1MHz/500kHz 又超时，**所以这版目前不能算烧录成功**。"
2. **用串口证明芯片活着**："先看 COM3 是否仍在跑旧固件；**如果旧遥测还在，说明板子没锁死**，只是这次写入不稳定。"
3. **用"新固件独有字段"证明版本**："好消息：RX 诊断版实际已经启动，**`rx=0` 字段出现了**，说明写入主体是完整的，OpenOCD 失败发生在校验尾段。"
4. **明确声明没做破坏性操作 + 降速阶梯 + 最后请人物理干预**："目前工具仍在等待 CMSIS-DAP 返回，**没有执行破坏性恢复操作**"；24MHz→1MHz→500kHz→100kHz 逐级降；仍失败 → "**需要你给小车主控断电重上电一次**，再重连无线烧录器"。

**对照我们**：这四步我们坑库里都有（探针失败分类、串口+SWD 双证芯片死活、build 时间戳证固件版本、不自动救砖），**是同一套结论从两个方向长出来的**——可以互相当验证。我们额外强的是**救砖能力**（`unbrick_flash.ps1` 真机救回过）；他们额外强的是**verify 更可靠**（`tools/flash.ps1` 用独立会话字节比对 + 关 work area，绕开不可靠的目标侧 CRC helper）。

## 4. 他们的六条协作纪律（我们缺的部分）

| 纪律 | 他们的做法（有原文佐证） | 我们的状态 |
|---|---|---|
| **拒绝把不确定当成功** | "所以我不会把它当作成功"；"这版目前不能算烧录成功" | 🟢 我们有（北极星） |
| **主动声明局限** | 灰度标定完成时主动说"标定目前保存在 RAM，**断电、复位或重新烧录后需要再次 `cal start`**" | 🟠 我们偶尔漏（"达标"后不总说清失效条件） |
| **机理→修法→后续验证，一条消息说完** | 白底误判那条："原因不是接线，而是标定极值把白底噪声映射成 0–60% 黑度…我会加入 60% 黑度死区…**修改烧录后需要再扫一次**" | 🟢 我们有 |
| **边做边写调试日志** | `docs/logs/bringup_log.md` 在会话里被 `apply_patch` **反复 Update**（不是事后补写） | 🟠 我们常常"这一轮结束才补日志" |
| **不凭图/丝印猜引脚** | "天猛星 wiki 很多引脚图是图片…完整 pinmux 还得靠 TI SysConfig/SDK 元数据交叉确认，**避免凭图瞎配**"；"不能只凭 A/B 名字猜靠 5V 还是靠 GND" | 🟢 我们有（证据阶梯） |
| **纠错落到文档 + commit，不停在口头** | 编码器排针方向连续答错两次 → "刚才我回答错了接口，抱歉" → 改文档 → commit `7430996` | 🟠 我们改文档，但不总是**当场** commit |

**他们那次连错两次的根因值得单独记**：把**同一器件的两个不同物理接口**（"独立编码器输出排针" vs "6PIN 电机插座"）混成一个来回答脚序。→ 已入坑库（"一个模块有多个物理接口时，先确认用的是哪个接口再谈脚序"）。

## 5. 长会话管理：13 小时压缩 3 次，靠什么不失忆

他们没有我们这套 hook + guide，靠的是**三份文档 + 一份规则**：

- `AGENTS.md` = 项目事实（路径/SDK/编译器/探针）+ skill 规则 + 构建烧录命令 + **里程碑阶梯** + 硬件安全 + **"哪份文档写什么"**
- `docs/hardware_interface.md` = 引脚决策
- `docs/serial_protocol.md` = **命令集与遥测字段契约**
- `docs/logs/bringup_log.md` = 真机流水（每条带实测数字）

压缩发生后，agent 只要重读这四份就能接上。**我们的对应物更强**（always 注入的 steering + `工程事实SSOT.md` + 坑库 + 归档 + 三个 hook），**唯一缺的就是 `serial_protocol.md` 这份"命令/遥测契约"**——而我们已经因为它缺失付过代价（固件改了遥测格式，`watch_serial.ps1` 静默失效）。

## 6. 备赛/赛中思路（他们的排法 vs 我们该怎么排）

### 6.1 他们的里程碑阶梯（写在 `AGENTS.md` 里，逐级不跳）

```
① 板级点亮 + 稳定编译/烧录/复位/串口
② 电机 PWM/方向 + 安全限幅 + 急停
③ 编码器测速 + 直线速度环
④ 灰度线感知 + 线位置误差
⑤ 路径状态机（A→B → ABCD → ACBD → 四圈）
(IMU 与屏幕明确写着"有用但不是第一轮阻塞项")
```

**关键在最后一句**：他们**一开始就把 IMU 和屏幕定为"非首轮阻塞"**，先用灰度 + 编码器把要求 1/2 拿下，IMU 是后来为了"出弯航向对不准"才加的。**这就是"先拿分、再优化"的排法。** 我们的对应教训：不要在陀螺没到货时把整条线堵住（我们 guide 里"陀螺未到货 → 用双轮位置环同步做走直/转圈"的降级路子正是同构，保持它）。

### 6.2 他们真实的做题顺序（从时间线还原）

| 时段 | 干了什么 | 里程碑 |
|---|---|---|
| 07-09 07:44–08:20（~40min） | 环境/工程识别、写 `AGENTS.md`、引脚表初稿 | 还没碰硬件 |
| 07-10 08:56–09:55（~1h） | 全部 BSP 驱动 + bring-up 命令集，首次编译烧录、串口通 | 驱动骨架 |
| 07-10 10:24–10:46（~22min） | 电机/编码器实测（含极性归一化、非法跳变=0）+ **灰度 8 秒扫线标定 + 白底误判修死区** | 感知可信 |
| 07-10 10:48–11:00（~12min） | **悬空轮双轮速度 PI**（FF/slew/限幅），多组目标验证 | 速度环 |
| 07-10 11:00–11:31（~30min） | 循迹半圆弧：反应式 PD → 加曲线前馈 + 编码器阻尼 → `tag qualified-arc-v2` | 循迹合格 |
| 07-11 05:44–06:20（~35min） | IMU 接入、零偏标定、90° 手转验证 1.9% 误差 | 航向可用 |
| 07-11 06:20–07:00（~40min） | 陀螺融合两次失败 → 定位到**整数目标量化**根因 → 定点化 → `qualified-continuous-arc-v3` | 循迹稳定 |
| 07-11 07:00–08:30（~1.5h） | 路线状态机 ACBD 分段 bring-up（pivot / 寻线 / 端点合议 / 各类 guard） | 全程跑通 |
| 07-11 15:00–17:30（~2.5h） | **硬件移交文档**（区分"工程已配置/仅预留/已实车验证"三档）+ 器件丝印核对 + 画板建议 | 交付 |

**两个刻度对我们最有用**：
- **驱动骨架 → 感知可信 → 单环 → 复合控制 → 状态机**，每级 20~40 分钟，**总共约 5 小时就跑完了要求 1/2/3**。剩下的时间全花在"稳定性 + 交付文档"上。
- **最后 2.5 小时全用来做硬件移交文档**——不是写报告，是**把"哪些脚已实车验证、哪些只是预留"分档交给画板的人**。这个"三档状态"分类法值得我们直接抄进 `工程事实SSOT.md`。

### 6.3 命令集 = 测试用例（他们 866 行 `app_bringup.c` 的真正含义）

他们的串口命令不是"调试口"，是**一套可复现的实验**：`motor <l> <r>`（1 秒自停）、`speed <l> <r>`（3 秒）、`follow <8..20>`（2 秒）、`followrun`（15 秒 guard）、`followarc <speed> <bias>`、`cal start/stop`、`imu cal`、`yaw zero`、`route3 ac/acb/cb/full`、`pi/lpd` 读写增益。

**每条命令 = 一个带时限、可重复、结果可量化的最小实验。** 这就是为什么他们能 5 分钟一个迭代——**实验成本被压到"发一行命令"**。我们已有 `m/t/p/i/d/w/e/f/x/y/g/z/?`，方向对，但缺三样：**① 分段实验命令**（走直 N mm / 原地转 N° / 循迹 N 秒）；**② 全部带固件侧时限自停**；**③ 遥测按视图分组 + key=value**。

## 7. 结论与行动项

**这个项目最值得学的不是控制算法，是"把不确定性挤出去的工程节奏"**：

1. 一个真机迭代压到 5 分钟（在线调参 : 重烧 = 3.4 : 1）
2. 每个实验都有时限、有口令、有量化判据
3. 每次失败先分类（链路/芯片/固件/逻辑），不先改代码
4. 每个里程碑打 tag、每条纠错落 commit、日志边做边写
5. 交付时把"已验证/仅预留"分档，不把猜测交给下一环

**落到我们身上的行动项（按可做性排序）**：

| # | 行动 | 成本 | 依据 |
|---|---|---|---|
| 1 | 真机测试**协议化**：AI 发起时给齐"放置/保持/开始口令/结束口令 + 先留基线" | 0（只是习惯） | §2；我们手推刚度测试 3 次脱节 |
| 2 | 补 **`docs/serial_protocol.md` 命令/遥测契约**（命令表 + 遥测字段 + 每条的时限） | 小 | §5；`watch_serial.ps1` 已因格式漂移失效 |
| 3 | 运动命令**固件侧时限自停** + 遥测改 key=value 分视图 | 中（动固件） | §6.3 |
| 4 | 新增**分段实验命令**（走直 N mm / 转 N° / 循迹 N 秒），配合施工序 3~6 | 中 | §6.3 |
| 5 | `工程事实SSOT.md` 引脚表加**"已实车验证 / 工程已配置 / 仅预留"三档状态列** | 小 | §6.2 交付段 |
| 6 | 日志纪律：**边做边写 `调试日志.md`**（每个真机动作当场记数字，不等收尾） | 0 | §4 |

**不要抄的**：他们的所有增益/阈值/几何数值（§5 of `02_逐层差距评判`）；他们的边沿中断编码器（我们 EMI 环境更差，采样解码更对）；他们 5 分钟一次的连续烧录节奏（我们 MSPM0 有 double-fault 锁死风险，必须靠在线调参替代）。
