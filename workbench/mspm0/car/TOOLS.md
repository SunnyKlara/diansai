## §0 赛场只需这 6 个（其余 61 个都是"出问题才翻"）

**都从 `car/` 目录里跑**（`tools\` 前缀就是路径的一部分，别 `cd tools`）：

| 顺序 | 命令 | 干什么 |
|---|---|---|
| 1 | `.\env_check.ps1` | **换机/到场第一件事**：一张 PASS/FAIL 表 + 工具链版本 + `car.out` 的 text+data（=烧录对账值） |
| 2 | `.\build.ps1` | 只编译不烧录（`-Touch` 强制重编）。**别用它烧板** |
| 3 | `.\flash.ps1` | 烧录（单会话全自动、含 stale-read 假失败识别）。判据 = `wrote N` + `verified N` == `size` |
| 4 | `.\tools\uart_send.ps1 -Cmd "?"` | 发一条命令读回显（逐字符 25ms，别改） |
| 5 | `.\tools\run_log.ps1 -Port <口> -Seconds N` | 跑一趟出成绩单（丢包/dt/编码器增量/yaw），有线无线都行 |
| 6 | `.\unbrick_flash.ps1` | **救砖**（`Could not find MEM-AP` 时唯一的命）。已全自动、不用手按 RST |

> ⚠️ **烧不进先分清是哪一种**：`flash.ps1` 用于 DAP 还活着的板；报 `Could not find MEM-AP` 才是 `unbrick_flash.ps1`。
> ⚠️ **看到 `verify` 报 `diff` 别直接重烧** —— 先 `.\verify_addr.ps1 -Addresses 0x4,0x7510` 只读复核（该假失败已第 5 次复现）。

## §3 重排是怎么切的（判据在这，别凭感觉再切一次）

**问题**：45 个 `.ps1` 和 28 个 `.c/.h` 平铺一个目录 —— 布局问题，跟"能不能跑"无关，但它让人找不到东西。

## §5 命名约定（原来很乱，已收口）

`car/` 里 `_` 前缀曾同时表示四种东西：**核心库**(`_tools.ps1`)、**模板**(`_tools.local.example.ps1`)、
**分析工具**(`_an.ps1`/`_turn.ps1`)、**一次性**(`_servo_oneshot.ps1`)，而 `.gitignore` 里 `_scratch*` 又用 `_` 表示"可丢弃"。
**这大概就是 `_an`/`_turn` 一度没被提交的原因** —— 它们看起来像草稿（现已入库，见 §4）。

⇒ **从现在起**：`_` 只留给 **`_tools*`（库/模板）与 `_scratch*`（可丢弃）**；新写的分析/测试工具**不要带 `_`**。
现有 `_an`/`_turn` 先按原名入库（`调试日志.md` 已按此名引用，改名 = 文档 churn），赛后连同 §3 第 4 步一起改。

### 🔴 读法规则：`tools/` 下的 `_` 前缀**不代表可丢弃**，实测 0 个是草稿

同一个 `_`，在两个目录里含义相反：

| 位置 | `_` 的含义 | 依据 |
|---|---|---|
| `03_报告/_*` | **一律不入库**（内部件/中间物） | `.gitignore` 有显式规则 |
| `car/tools/_*` | **库 / 自测 / lint / 分析工具**，全部入库 | 见下面的实测 |

`car/tools/` 下 7 个 `_` 开头的 tracked 文件，逐个看过：**4 个是库/自测/lint**（`_serial_ball` `_fit`
`_fit_test` `_fmt_check`，O 组）、**3 个是带完整机理说明的分析工具**（`_an` `_turn` `_servo_oneshot`），
**可丢弃的 = 0 个**。真正的草稿是 `_scratch_*`，它们按 `.gitignore` 根本不在 git 里
（磁盘上 `car/` 根 25 个 + `tools/` 若干，tracked 恒为 0）。

**⇒ 危险的具体形态**：谁把报告目录那条"`_*` 不入库"的直觉带到 `tools/`，就会漏提或删掉
`_fit.ps1`/`_serial_ball.ps1` —— 而 `ball_bringup`/`ball_ident`/`ball_signs` 三个都 dot-source 它们，
**clone 下来一跑即挂**。本仓库已经栽过三次同型的跟头：`uart_frame.h` 孤儿头（无 `.c`、不在 makefile、从未编译）·
`esp_fake_mcu.ps1` 自称 "faithful copy of `car.c` cmd_format_ok()" 而原件不存在 ·
11 个脚本写死 `C:\ti` 在队友机上全挂（暴露时机正是芯片 lockup、救砖脚本是唯一通道时）。

**复核判据（判官是 `git ls-files`，不是磁盘）**：每个 tracked 脚本的 dot-source 目标必须也是 tracked。
2026-07-31 实跑：**99 个 tracked `.ps1` / 0 处未解析**（另 209 处 C 的 `#include` 是 SDK/工具链/生成物
—— `ti_msp_dl_config.h` 是 SysConfig 生成且刻意 gitignore、`esp_log.h`/`freertos/*` 是 ESP-IDF、
`stm32h7xx_hal_*` 是 ST HAL —— 属外部依赖，不在本判据范围内）。
