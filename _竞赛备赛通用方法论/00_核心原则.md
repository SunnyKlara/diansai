# 核心原则（七条不可让步）

> 这七条是从电赛仓库实战中打磨出来的，跨比赛通用。直接拷贝。

---

## 原则 1：三大模块物理隔离

任何比赛仓库都强制分三个一级模块：

```
<仓库根>/
├── _历史参考/    # 上届/上届的上届的成果，**只读**
├── 备赛系统/      # 本届主战场，所有新增进这里
└── _原始资料/    # 官方规则、题目、PDF，**只读**
```

理由：

- **混在一起 = 不知道谁是金标准**：新人不知道"哪个工程是能直接用的"
- **只读保护**：避免老队员的稳定版本被新人误改

工程上：在仓库根 `README.md` 头部明确这三个目录的"读写权限语义"，用文字约束。

---

## 原则 2：真题（或赛事单元）目录强制六件套

每个"作战单元"（电赛的一道题 / RM 的一台机器人 / ICPC 的一场赛 / 数模的一年题）必须包含：

| 序号 | 文件夹 | 内容 | 必备性 |
|---|---|---|---|
| 00 | `00_审题/` 或顶级 `.md` | 题意、指标分解、约束、风险 | ✅ |
| 00x | `00_深度论证.md` | 多方案对比 + 评分表 | ⚠️ 重点单元 |
| 01 | `01_代码/` | 工程代码（按层分目录） | ✅ |
| 02 | `02_硬件/` 或 `02_数据/` | 实物 / 数据集 / 输入素材 | ✅ |
| 03 | `03_报告/` 或 `03_论文/` | 提交物草稿 + 终稿 | ⚠️ 完赛后必备 |
| 04 | `04_调试记录/` | 检查清单 + 独到经验总结 | ✅ |

**缺哪个就建占位文件**。不要因为"还没做"就空着 —— 占位符本身就是 TODO 提醒。

跨比赛映射：

| 比赛 | 作战单元 | 02 是 | 03 是 |
|---|---|---|---|
| 电赛 | 一道真题 | 02_硬件 | 03_报告 |
| 智能车 | 一年赛道 | 02_机械结构 | 03_技术报告 |
| RM | 一台机器人 | 02_机械 + CAD | 03_整合报告 |
| ICPC | 一场比赛 | 02_补题 | 03_赛后复盘 |
| 数模 | 一道年题 | 02_数据 | 03_论文 |

## 原则 3：方向训练 + 通用能力 双轨制

```
备赛系统/
├── A_方向训练/       # 按"赛道/兵种/算法专题"垂直分类
│   └── <方向名>/
│       ├── 00_方向总览与训练计划.md
│       ├── 01_基础库/   # 模块化片段，一文件一主题
│       └── 02_进阶/
└── C_通用能力/        # 跨方向的横向能力
    └── <能力名>/
```

**A 是"打哪场"，C 是"用什么打"**。两者交叉引用但不重复。

例：电赛 RM 都用 PID，PID 文档放 `C_通用能力/PID控制/`，电源方向、智能车方向都引用它，不在各自方向里再写一份。

## 原则 4：Markdown 强约束写作

| 项 | 约定 |
|---|---|
| 首行 | 必须是 H1 一级标题 |
| 表格 | 涉及指标/参数/对比 → 用表格，不用段落 |
| 代码块 | 必须标语言：` ```c `、` ```python `、` ```cpp ` |
| 器件/库引用 | 完整型号 + 关键参数 + 数据手册/官网链接 |
| BOM/材料 | 必须含 序号 \| 名称 \| 型号 \| 参数 \| 数量 \| 用途 \| 备注 |
| 行宽 | 不强制，但鼓励一行一句，方便 Git diff |

为什么强约束？—— **AI 读起来效率翻倍，diff 可读，跨人协作不打架**。

## 原则 5：代码分层硬隔离

不论比赛，所有工程代码都按三层（或四层）拆：

```
01_代码/
├── Core/        # main、状态机、业务编排
├── Drivers/     # 硬件抽象层（HAL）/ 数据 IO
├── Algorithm/   # 纯计算 / 算法 / 模型
├── config.h     # 集中可调参数
└── README.md    # 编译/运行说明
```

铁律：

- **驱动里禁止写业务**（不能在 `motor.c` 里判断"是否到终点"）
- **算法里禁止碰硬件**（不能在 PID 里直接读 ADC）
- **可调参数全进 `config.h`** —— PID 系数、采样率、阈值、超时

ICPC 适配：分 `template/`（模板库）、`solutions/`（题解）、`stress/`（对拍工具）。
数模适配：分 `data_io/`、`models/`、`viz/`。
精神一致：**让人能在不读完整工程的前提下改任何一层**。

## 原则 6：Git 提交节奏 + Steering 双轨

提交：

- commit 格式 `<类型>: <简述>`，类型限定 `feat / fix / docs / refactor / test / chore`
- 一次 commit 一个目的，不要"杂烩 commit"
- 不直接 push main，feature 分支 + PR
- `.gitignore` 严防 `*.apk / .env / 私钥 / Keil 编译产物 / 证件`

Steering（AI 协作配置）：

- `.kiro/steering/<仓库名>规范.md` 必须存在
- 规范里定义：目录结构、命名约定、AI 自主执行边界、用户交付契约
- 改 Steering = 改"AI 队员的行为准则"，比改代码还重要

---

## 原则 7：AI 自主执行契约（最重要）

**用户对 AI 的承诺**：你做完整批次再来汇报，过程不打扰。
**AI 对用户的承诺**：

1. **不反复请示**。能猜的猜，决策痕迹留在文档里事后可推翻
2. **不索要权限**。仓库内的文件创建/编辑/批量生成是低风险，直接干
3. **遇错自愈**。编译错自己修；缺资料按公开文档兜底；信息空白标 TODO 继续推进
4. **批量一气呵成**。"刷完 N 道题"类任务循环产出，全部完成再统一汇报
5. **验收只看结果**：交付物齐全可用即合格，过程犹豫和反复确认 = 失败

高破坏性操作（`git push --force`、删整个目录、对 main 操作、改密钥）才需要确认。

## 跨比赛通用决策清单

每开一个新仓库时，按这张表决策：

| 决策项 | 选项 | 默认推荐 |
|---|---|---|
| 主语言 | C/C++ / Python / Verilog / Java | 看比赛 |
| 工程框架 | CubeMX / PlatformIO / CMake / Makefile | CMake（可移植） |
| 文档格式 | Markdown / LaTeX / 双轨 | Markdown 主导，论文用 LaTeX |
| AI 工具 | Kiro / Cursor / Claude Code / Copilot | 至少一个有 Steering 能力 |
| 协作方 | GitHub / Gitee / GitLab | 看团队 |
| Issue 跟踪 | GitHub Issues / 飞书 / 钉钉 | GitHub Issues + 周会 |

## 不可让步线

下面这些事**任何理由都不能妥协**，否则系统会塌方：

1. ❌ 真题/作战单元目录里没有"六件套占位"
2. ❌ Driver 层里写业务逻辑（或反之）
3. ❌ 调参数硬编码在算法里、不放 `config.h`
4. ❌ 仓库里出现 `.env`、私钥、个人证件、`.apk`
5. ❌ AI 协作每一步都来问"是否继续"
6. ❌ commit message 写"update / 修改"等无意义内容
7. ❌ 直接 push main 不走 PR
